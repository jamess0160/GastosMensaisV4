Guidance for the API side of this repository.

**The rules that span both sides live in the [repository root's CLAUDE.md](../CLAUDE.md)** and
are not repeated here: the commit convention, where the documentation lives, the money

## Commands

- `npm start` — run the API in dev mode via nodemon (`tsx index.ts`, restarts on `.ts`/`.js` changes, ignores `Logs/*`).
- `npm test` — run the integration suite (Jest in-band, config in `jest.config.ts`); `npm test -- Users` filters by file. `npm run test:watch` re-runs on change. See "Integration tests" below.
- `npm run start:test` + `npm run test:e2e` — the end to end pair: the first boots the API with `NODE_ENV=test` (test database, port 4100), the second points the same suites at it via `TEST_BASE_URL`. Both go through `cross-env`, since `VAR=value cmd` doesn't work in the Windows shell npm uses.
- `npm run build` — full build: `build:app` (webpack bundles `index.ts` → `build/bundle.js`, `node_modules` excluded via `webpack-node-externals`) + `build:migrations` (`tsc -p tsconfig.migrations.json` compiles `migrations/*.ts` → `build/migrations` **and `knexfile.ts` → `build/knexfile.js`**, dragging along the handful of `Utils/` files the knexfile imports). Migrations compile apart from the app bundle because the Knex CLI loads them as files, one by one, and reads no bundle — and the knexfile rides with them for the same reason: it is the only thing that says which database to migrate, and inside the image there is no ts-node to read the `.ts`. `build/` is gitignored; nothing here is versioned.
- Migrations, all four through npm scripts (Knex CLI, config in `knexfile.ts`): `npm run migrate` (latest), `npm run migrate:rollback`, `npm run migrate:make <name>` — and `npm run migrate:prod`, the same `migrate:latest` against the compiled `build/knexfile.js`, which is what the deploy calls. Before this they were remembered `npx knex` lines with no script at all, and the first deploy would have died before the first request.
  - **The knexfile exports one config object under three keys — `development`, `test` and `production` — not three copied blocks.** The CLI picks the key by `NODE_ENV`, defaulting to `development`; only `development` existed, so `NODE_ENV=production` (mandatory at deploy) looked for a key that was not there and failed. One object and three references because three copies diverge the day somebody adds a pool option, and **which database each one is was never the file's answer** — it is the `.env`, the `.env.test` layered over it, or the deploy environment.
  - **The file has no `dotenv.config()` of its own**, and that absence is deliberate: importing `enviromentManager` already runs `Utils.configEnv()`, the exact `.env` + `.env.test` load the API does. The `dotenv.config()` that used to sit there ran *after* it anyway (imports are hoisted) and read only the `.env` — harmless, but it read as if the CLI loaded its own environment, which is how `NODE_ENV=test npm run migrate` would end up pointed at the development database.
  - **`migrations.directory` is `path.join(__dirname, "migrations")`, never `"./migrations"`.** The Knex CLI **chdirs into the knexfile's folder** (it says so on stdout), so the same relative path means two different folders from the two knexfiles — and from `build/` it would find the `.ts` sources it cannot load.
  - **Never point `migrate:prod` at a database that `migrate` has touched.** `knex_migrations` stores the file name *with its extension*, so a `.js` run sees the recorded `.ts` rows as missing files and refuses with "the migration directory is corrupt". It is not a real conflict: a production database is only ever migrated by `migrate:prod` and a development one only by `migrate`. Mixing them is what breaks.
- No lint script is configured.

## Environment

- Env vars load through `Utils.configEnv()` (`Utils/Utils.ts`), which reads `.env`, or `.env.test` when `NODE_ENV=test`. `exemple.env` documents the full var list (`PORT`, `DB_CLIENT`, `DB_HOST`, `DB_LOGIN`, `DB_PASSWORD`, `DB_SCHEMA`, `DB_PORT`, `JWT_SECRET`, `WEBAUTHN_RP_ID`, `WEBAUTHN_RP_NAME`, `WEBAUTHN_ORIGIN`, `MAIL_SMTP`, `MAIL_SMTP_PORT`, `MAIL_SMTP_SECURE`, `MAIL_USER`, `MAIL_PASSWORD`, `MAIL_FROM`, `APP_URL`).
- **`NODE_ENV` is the only variable that says which environment this is, and it is asked in one place.** `Utils/environment.ts` exports `isProduction()` and `isTest()`; nothing else compares `NODE_ENV` by hand. Between them they decide the cookie's `secure` (`AcessControl`), the log transport — stdout in production, a file in development (`Utils/Logs.ts`, see Logging below) —, the mailer's `jsonTransport` (`Utils/Connections/Mailer.ts`), the `.env.test` layered over the `.env` (`Utils.configEnv`) and the routine engine being off in the suite (`index.ts`). **Absent means development** — the one var whose absence is an answer instead of a boot error. There used to be a second variable saying the same thing: `PROD`, known only to `AsyncHandler` and documented nowhere, so in production — without somebody guessing it existed — every route error printed its whole object to the container's stdout. It is gone; that `console.log` is now gated by `!isProduction()`. A function rather than the comparison repeated in two files is what stops the third place from testing for `"prod"` or `"PRODUCTION"` and working everywhere except where it matters. Setting `NODE_ENV=production` in the deploy environment is infra's half of it — this side is only the code that behaves correctly once it is set.
- All env access goes through `enviromentManager.getEnv(key, optional?)` (`Utils/enviromentManager.ts`), never `process.env` directly. **`Utils/environment.ts` is the single deliberate exception**, and it has to be: `configEnv` consults the environment to decide whether to load `.env.test` — that is, *before* any `.env` has been read — and `enviromentManager` calls `configEnv` in its own import, so routing this one question through it would close an import cycle. Nothing is lost, since `NODE_ENV` never comes from a `.env`: it comes from `cross-env` in the npm scripts, from `TestEnv` in the suite, or from the deploy environment. It is also read on every call rather than captured at import, because `Mailer.test.ts` flips it at runtime to prove the SMTP transport. Values are read as-is from the `.env`; a missing var throws an `APIError` at boot unless `optional` is `true`, in which case it returns `""`. The `.env` itself is what protects the secrets, so keep it out of git and restrict its file permissions — there used to be an AES layer here with the key hardcoded in the repo, which is why it was removed rather than fixed.
- **The two log switches are code, not configuration**: `Utils/logFlags.ts` exports `{ routeErrors, rotine }`, imported by `AsyncHandler` and by `RotineEngine`. They used to live in a `Utils/constants.json` inherited from another project, read from disk — `fs.readFile` + `JSON.parse` — **on every request**, before the access middleware, to be spent on a single line inside the `catch`; the file's other keys were `MssqlMaxParameters` and OEE indicator types. `Utils.getConstants()`, `CONSTANTS_PATH` and the JSON are gone: these are development flags that change with the code, so an env var would only add one more thing to forget at deploy, and as a TypeScript module a misspelled flag is a compile error instead of a production surprise.

## Architecture

Express + TypeScript API using Knex over PostgreSQL (client is configurable via `DB_CLIENT`). Path alias `root/*` maps to the repo root — used everywhere instead of relative imports across features (wired via `tsconfig-paths/register` for `ts-node`/`tsx`, and `TsconfigPathsPlugin` for webpack).

### Feature module layout

Each feature lives under `routes/<Feature>/` (see `routes/Users/`, `routes/Workspaces/`, `routes/UsersAuth/`, `routes/Utils/`) with a consistent split:

- `<Feature>.route.ts` — an `express()` sub-app with route definitions; every handler is wrapped in `AsyncHandler`, often preceded by a schema validator. All sub-apps are collected into the `Routes` array in `routes/index.ts` and mounted via `server.app.use(Routes)`.
- `<Feature>.controller.ts` — thin: pulls params/body off `req`/`res.locals`, delegates to a class in `sections/`, calls `res.json(...)`.
- `<Feature>.schema.ts` — Joi schemas wrapped by `joiController` (`Utils/joiController.ts`): `validateBody`/`validateParams`/`validateQuery`/`validateResponse`. Each returns middleware built from `AsyncHandler(fn, requireToken=false)`, so schema validation itself never requires auth even when the route does.
- `<Feature>.model.ts` — a `class_X_model extends BaseModel` (`Utils/Base.ts`) exposing the injected `KnexConnection` as `this.KnexConnection`; holds the Knex queries for one primary table. One model file per table, always.

**A table that has routes of its own gets its own feature folder** — `routes/Accounts/` and `routes/PaymentMethods/` are separate even though the payment method is the child of the account. A table with no routes of its own stays a second model file inside its parent's folder (`Workspaces/WorkspaceMembers.model.ts`, `UsersAuth/TrustedDevices.model.ts`): it's reached only through the parent's sections, so it has nothing to put in a route/controller/schema. Cross-feature calls go through the `root/*` alias, never a relative path out of the folder.

**`routes/Reports/` is the one folder with no table of its own**, and the exception is deliberate: it is the feature that reads from all the others. It has a route, a controller, a schema and sections — everything except a model, because it owns no row. Its sections **delegate and never recalculate**: `AccountBalance` already holds the rules, and `Reports` is one more caller beside the controller and the test. (`BudgetSpent` is named the same way in some comments, but `Reports` has never called it — no budget number reaches `/Reports/Month`.) The day a section there needs a filter of its own is the day it started diverging from the number the rest of the app shows.
- `sections/` — business logic, one class per operation (e.g. `GET/getSelf.ts`, `POST/create.ts`), each with a `run()` method the controller calls; plus feature-local support files like `AcessControl.section.ts` and a `types.ts` namespace for payload types.

Follow this same file split (route/controller/schema/model/sections) when adding a new feature or endpoint rather than putting logic directly in the controller.

### Request pipeline

`AsyncHandler` (`Utils/AsyncHandler.ts`) wraps every route handler and is the single place that: enforces auth (calls `Users_controller.acessMiddleware` unless `requireToken` is explicitly `false`), awaits the handler, and catches errors — logging via `Logs.handleError` (gated by `logFlags.routeErrors`), replying with `{ msg }` + `error.status` for a thrown `APIError` (`Utils/Logs.ts`), or a bare 500 otherwise.

Auth is JWT-based (`routes/Users/sections/AcessControl.section.ts`): `acessMiddleware` reads the token from the **httpOnly `token` cookie — and only from there** — verifies it with `JWT_SECRET`, and sets `res.locals.IdUser` and `res.locals.IdWorkspace` on success (typed via the `Express.Locals` augmentation in `Utils/Globals.d.ts`). `cookie-parser` is mounted in `Utils/server.ts` for exactly this: express writes cookies (`res.cookie`) but does not read them, so without it `req.cookies` is undefined and every protected route answers 401.

**There is no `authorization` header path, deliberately.** Two ways in means the weaker one decides, and a header accepted from anywhere escapes the `sameSite: 'strict'` that is the whole CSRF defense now that the browser attaches the credential by itself. `Users.test.ts` locks this in: a perfectly valid token sent in the header is a 401. The cookie's three attributes carry the session's security and are asserted, not assumed — `HttpOnly` (an XSS cannot read the token), `SameSite=Strict` (the browser never attaches it to a cross-site request; CORS would not help, since CORS governs who reads the response, not who sends the request), `Max-Age=86400` (dies with the token).

**Deployment assumes same origin.** The front-end is served from `www.gastosmensais.com.br` and the API from `www.gastosmensais.com.br/api` behind nginx: same scheme, host and port, so the browser never treats these as cross-origin — no CORS, no preflight, and the cookie rides along. In development, front and API on different ports **are** different origins, which `sameSite: strict` blocks: proxy `/api` through the dev server (Vite `server.proxy`) so dev matches production instead of loosening the cookie. And `NODE_ENV` must actually be `production` at deploy, or `secure` is never set on the cookie.

**There is no `cors()`, and the absence is the decision** (`Utils/server.ts`). It used to be mounted wide open — `Access-Control-Allow-Origin: *` on every response — described here as "inert in that setup", which was true only for as long as the nginx config it assumed existed. It was not replaced by `cors({ origin: APP_URL })`: with one origin the browser emits no preflight and there is no cross-origin response to allow. The day a client on another origin exists, it comes back with the origin decision written next to it — and the answer is never to loosen the cookie. `Users.test.ts` asserts the missing header on a plain response, beside the `nosniff` that proves helmet is up.

**Three more things the same file settles, all invisible on `localhost`:**

- **`app.set('trust proxy', 1)`** — one hop, the one that exists between nginx and this process. Without it every request appears to come from `127.0.0.1` (an IP-keyed count that counts the whole world as one person) and `req.protocol` is `http` even for a user on https, which is what would silently switch off the HSTS below. `true` would trust the whole `X-Forwarded-For` chain, letting any client pick the IP the Express sees by sending the header.
- **`express.json({ limit: '100kb' })`** — the same value body-parser defaults to, written by hand so it is a decision instead of a side effect of the dependency's version. The 413 it produces is the app's one response that passes through no route at all: the parser answers before `AsyncHandler` exists, which is why helmet is mounted **before** it — so that response carries the same headers as every other.
- **`helmet()`, with two options spelled out.** `contentSecurityPolicy: false`: this port answers JSON (and one `.xlsx`), and the CSP that matters is the **page's**, served by nginx — turning one on here would protect an HTML document the API never returns while making the subject feel handled. `crossOriginResourcePolicy: { policy: 'same-origin' }`: helmet's own default, written out because it is the same same-origin design as above, and it is *that* line that moves the day another origin has to read a response from here. The HSTS helmet turns on only ships when the request arrives as `https`, which is exactly what `trust proxy` makes the Express see — the two belong together.

Every login ends at `AcessControl.startSession(res, IdUser)` — it resolves the default workspace, issues the token carrying both ids, and stamps `LastLogin`. Both credential paths (password and biometrics) call it and nothing else emits a token, so the two can't drift apart in what they record.

Signup (`POST /Users`) creates the **user, their workspace and their own `Persons` row in one transaction** (`routes/Users/sections/POST/create.ts` + `routes/Workspaces/sections/POST/create.ts` + `routes/Persons/sections/POST/createSelf.ts`) and returns `{ IdUser, IdWorkspace }`. Every domain table is scoped by `IdWorkspace`, so a user without one can't record anything — half an account. The workspace also gets its `WorkspaceMembers` row in the same transaction: reads go through membership (`Workspaces_model.getByMember`), so a workspace without it is an orphan tenant nobody can see. And every split is between `Persons`, never `Users`, so without that row the owner couldn't appear in their own split — `createSelf` is the **only** writer of a person's `IdUser`, and the value comes from the user just inserted, never from the body. It is skipped (not renamed, not refused) when the name is already taken in a workspace being joined, since `unique(IdWorkspace, Name)` would otherwise let a namesake bring the whole signup down. A workspace is born in exactly two places: signup, and `POST /Workspaces` (`routes/Workspaces/sections/POST/createOwn.ts`), which is the same three writes for a user who already has an account — workspace, membership as `owner`, and their own `Persons` row — and is the one route in the feature that checks no membership, since the workspace doesn't exist yet. It does **not** re-issue the token, exactly like `join`: creating grants membership, it doesn't move the session, and `switch` stays the only route that changes the selection.

**The session is two things — who you are (`IdUser`) and which workspace you're in (`IdWorkspace`) — and both ride inside the same signed token.** `acessMiddleware` reads the token once and puts both on `res.locals` (typed in `Utils/Globals.d.ts`). `POST /Workspaces/switch` is the only route that takes an `IdWorkspace` written by the client; it checks membership and then **re-issues the token**, because the token is what carries the selection. `AcessControl.startSession` selects the user's first workspace on every login (`SelectDefault`), so a session never starts without one and `switch` really is a switch.

The token is **signed, not encrypted** — a JWT payload is base64, so anyone holding it reads `IdUser` and `IdWorkspace` in the clear. Never put a secret in there. What the signature buys is the thing that matters here: the client cannot swap the workspace for another one. What it buys over a second cookie of its own: a separate `IdWorkspace` cookie would be client data, rewritable to any sequential id — inside the signed token that door is shut, and the whole session lives and dies as one cookie.

**Signed is not the same as still true, so `assertMember` stays.** The token is a snapshot of the authorization taken at login and it lives 24h: membership can be revoked, or a role downgraded, after it was issued. Authentication the token settles; authorization only the database can answer. So every tenant-scoped section still starts with `WorkspacesAcessControl.assertMember`/`assertRole` (`routes/Workspaces/sections/AcessControl.section.ts`) — and note 7 of the 9 call sites are `assertRole`, which needs the *current* role and would have to hit the database regardless. Those return the **membership row**, and sections use the `IdWorkspace` that comes back from it — never the one that arrived, which is named `SelectedIdWorkspace` in every signature precisely so a stale value can't reach a query by accident. A token with no workspace answers 406 "Nenhum workspace selecionado" (the fix is `switch`); not-a-member answers 406 "not found", not 404 — a 404 would confirm the workspace exists.

**Member management is five routes, and all five address the membership — never the user.** `IdWorkspaceMember` is scoped to the workspace by birth; `IdUser` is global and crosses tenants, so no route accepts one and `GET /Workspaces/members` doesn't even return one. Every one of them reads the target with `WorkspaceMembers_model.getUnique(IdWorkspace, IdWorkspaceMember)` — the `IdWorkspace` coming from the membership `assertMember`/`assertRole` returned, never from the token — and answers 406 "Membro não encontrado!" when it misses, because the id arrives from the client and is sequential.

- **`GET /Workspaces/members`** opens with `assertMember`, not `assertRole`: whoever shares the space has a right to know with whom. Returns `Name`/`Email` (joined from `Users`), `Role`, `JoinedAt` (the *membership's* `CreatedAt`) and `IsSelf` — which describes the token that answered, not the row, exactly like the workspace's `Current`.
- **`PUT /Workspaces/members/IdWorkspaceMember=:Id`** — `assertRole(["owner"])`, body `{ Role }`. Only `editor`/`viewer`: `owner` is refused by the Joi, before the section, because promoting to owner is *transferring ownership*. The owner changing their own role is 406, or the space would be left with no owner and no route to fix it.
- **`DELETE /Workspaces/members/IdWorkspaceMember=:Id`** — `assertRole(["owner"])`. The membership is **physically deleted**, and that is why `WorkspaceMembers` has no `Active`: an inactive membership is revoked access still occupying `unique(IdWorkspace, IdUser)`, which would come back on its own at the next invite to the same address. **Nothing the person recorded is touched** — expenses, inflows and accounts belong to the *workspace*, and "who spent it" points at `Persons`, another table with no relation to who has a login, so no balance and no split moves by one cent.
- **`DELETE /Workspaces/members/self`** — no id in the path: the membership it deletes is the one `assertMember` returned, so there is nothing to check against anything. The guard is the **opposite** of remove's: it requires *not* being the owner, and refuses with a 406 of its own rather than the generic 403, because the error has to name the next step — transfer the ownership.
- **`POST /Workspaces/members/IdWorkspaceMember=:Id/transferOwnership`** — `assertRole(["owner"])`, no body, and the target can't be the caller's own membership (that would write the same state under another name). **Three writes in one transaction**: the target's role becomes `owner`, the caller's becomes `editor` — not `viewer`, since whoever hands over the key shouldn't lose write access in the same click; downgrading further is the new owner's call — and `Workspaces.IdOwnerUser` moves to the target. The third write is not optional: **ownership is stored in two places that don't derive from each other.** The membership's role is what `assertRole` reads and the only thing that authorizes; `IdOwnerUser` is what `GET /Workspaces/getSelf` exposes and what the client reads to decide what to offer on screen. Moving one without the other leaves the API and the client disagreeing about who is in charge. Outside a transaction, a failure between the writes leaves the space with two owners or none, and neither state has a route that fixes it — every management route needs an owner to be called.

**None of the five reissues the token, and none needs to.** The session's workspace is the same before and after; what changes is the *role* inside it, and the role was never in the token — `assertRole` answers for it from the database on every request. Which is also why the old owner keeps working with the very same cookie: the invite routes start answering 403 to them and `leave` starts working, with nothing re-logged in.

`AcessControl` owns the cookie: `setTokenCookie` writes it (login, and `switch` when it reissues the token), `clearTokenCookie` drops it. Nothing else emits a session.

**Password recovery is a short JWT with no table of its own** (`routes/Users/sections/ResetPasswordToken.section.ts`) — the same pattern as the biometrics `ChallengeToken`, which already solves this problem here: prove a value came from the API and not from the client, without keeping state between two requests. **Single use falls out of the construction:** the token carries `{ IdUser, type: 'reset' }` plus a fingerprint of the current password hash (a truncated sha256 of it, not the bcrypt itself — a JWT payload is base64 and travels by email), so changing the password makes the fingerprint stop matching and the link dies on its own. No table, no cleanup routine, no revocation list. `type` is mandatory for the same reason it is in the biometrics challenge: a token signed with the same `JWT_SECRET` for another purpose must not be spendable here. `POST /Users/forgotPassword` answers **200 always**, with the same `msg` for an address that has an account and one that does not — otherwise the route is a checker for which emails are registered, exactly what the login avoids by using one message for wrong email and wrong password. The email link points at the **front** (`APP_URL/recuperar-senha?Token=…`), which is what keeps it from being a `GET` that changes state. **The public routes carry a real brake now** (`routes/Users/sections/RateLimits.section.ts`): `express-rate-limit` on exactly four of them — `forgotPassword` and `resendConfirmation` 5 per hour, `login` 20 per 15 minutes, `POST /Users` 10 per hour — mounted **before each route's schema**, so a request over the ceiling costs no Joi, no query and no bcrypt. **Keyed by IP, never by email:** the caller picks the email field, so a per-address ceiling is dodged by changing one letter *and* lets an attacker lock somebody else's recovery. There is deliberately no global limiter (it would count a legitimate dashboard beside the attack), and the 429 body is the same sentence on all four, saying nothing about whether the address has an account — the brake must not become what tells the two apart. Storage is the `MemoryStore`: one process, counts zeroed by a restart, and the day there are two instances it becomes an external store. The suite keeps the brake **on** and calls `RateLimits.reset()` between tests — which is how one test proves the 429 while the rest of the file creates users in series; in end to end mode that reset can't reach the server's process, same limitation as the mailbox. `MailCooldown.section.ts` stays beside it and answers something else — the same person clicking twice for the same address — see the mail section below.

### Biometrics (WebAuthn), `routes/UsersAuth/`

Passkey login, carried over from V3's `webAuth` (`@simplewebauthn/server` v13). Two two-step flows — ask for options, return the signed assertion — stitched together by a `ChallengeToken`:

- **The challenge is a short JWT, not a session.** V3 parked it in a server-side session; here the API keeps no state between the two steps, so `WebAuthnChallenge` signs `{ challenge, type, IdUser? }` with `JWT_SECRET` for 5 minutes and the client returns it in the POST body. Signing rather than echoing is the whole point: a client-chosen challenge isn't random and opens replay. `type` lives inside the token so a register challenge can't be spent as a login one, and `register` additionally checks `challenge.IdUser` against the token's user, or a challenge lifted from another account would pin a passkey on the wrong one.
- **`DeviceKey` is not a credential** — it's a 32-byte base64url id the API generates and the device stores. It only answers "which credentials to offer here" and "have I already asked about biometrics on this device". Authentication is the passkey signature, nothing else. base64url (not V3's base64) because it travels as a URL param.
- **The user is resolved from the credential, not the device.** Login options take a `DeviceKey` and may return several `allowCredentials` (two people can enrol on one phone); `authenticate` looks up the `CredentialId` that came back signed. `Counter` is written back on every login — that's what keeps the lib's clone detection working.
- **`checkDevice` is tri-state**, like V3's `checkUser`: `true` = passkey here, `false` = the user declined here (`TrustedDevices`, V3's `ignoreauth`, written by `skipDevice`), `null` = never asked. Registering clears the decline.
- Public routes are exactly the ones a device without a token needs: `checkDevice`, login options, `authenticate`. Enrolling and removing credentials require a password session.
- Removal is a soft delete: the row stays so its `CredentialId` keeps the unique index occupied, otherwise an authenticator still holding the passkey could re-register it as new.

Passwords are hashed server-side and only there: `PasswordHasher` (`routes/Users/sections/PasswordHasher.section.ts`, bcrypt cost 12) is the single place that hashes and compares, used by `create`, `update`, `updatePassword`, `resetPassword` and `validateLogin`. The client sends the plaintext password in the **body** — never in the URL, since the path reaches the proxy access log, the browser history, the `Referer` header and `Logs.handleError` via `req.originalUrl`; that's why `POST /Users/login` and `PUT /Users/updatePassword` take a body instead of route params. `AsyncHandler` runs `Utils.redactSensitive` over `req.body` before logging, and `getSelf` strips `Password` from the response. Don't pre-hash or encrypt the password on the client: whatever the API receives becomes the effective credential, so a leaked hash could be replayed as-is.

### Database (Knex)

- `Utils/Connections/Knex/KnexConnection.ts` builds the shared `KnexConnection` from the `DB_*` env vars, and exports `KnexTransaction(fn)` — wraps `knex.transaction`, passing a `TransactionEvents` (`section/transactionEvents.ts`) so code inside a transaction can register `attachOnEnd(fn)` callbacks that fire after the transaction resolves. Models return QueryBuilders, so a section running inside a transaction enlists each query with `.transacting(tx)` (see `routes/Users/sections/POST/create.ts`) instead of building a second set of models.
- `DBTypes` (same file) maps table name → row interface. Row shapes themselves live in `Utils/database.ts` under the `Database` namespace. When adding a table, add its interface to `Database` and register it in `DBTypes` — this is what gives `joinTables` its type safety.
- Two custom QueryBuilder methods are registered globally in `Utils/Connections/Knex/AppKnex.ts`:
  - `.joinTables({ tableName: { selfPath, destinyColumn?, type?: "single"|"multi", append? } })` (`section/JoinTables.ts`) — fetches related rows from another table and attaches them onto the result (single object or array), based on `DBTypes`. Use `append` to further filter/shape the sub-query. It applies **no implicit filter**: only the registration tables carry `Active` (see below), and filtering it is each model's job via `append: (q) => q.where("Active", true)`. The name is `joinTables` (not `join`) because Knex's `.join()` is native and `QueryBuilder.extend` throws at boot on a name collision.
  - `.returnId(idColumnName)` (`section/returnId.ts`) — only valid on a single-row insert; returns the inserted id, branching on `DB_CLIENT` (mysql/mysql2 uses the insert id, other clients use `.returning("*")`).

#### Schema conventions

Tables are PascalCase plural, PK is `Id<Singular>` via `table.increments(...)`. Money is always `decimal(15,2)`, never float. Every table has `CreatedAt` and `UpdatedAt`; there is no `ON UPDATE` in Postgres, so every model sets `UpdatedAt` itself.

`Active` means soft-delete/archive and exists on every registration table: `Users`, `UsersAuth`, `TrustedDevices`, `Accounts`, `PaymentMethods`, `Categories`. Elsewhere the lifecycle comes from a `Status` column or the row cascades from its parent.

Domain tables are scoped by `IdWorkspace` (tenant) with `IdUser` as author. A user can be in several workspaces and a workspace can hold several people: `WorkspaceMembers` is that membership, and the `Role` on it (`owner`/`editor`/`viewer`) is what every write is authorized against. It has no `Active` on purpose — see member management under the session above.

**An account has no stored balance.** `Accounts.InitialBalance`/`InitialBalanceDate` are the opening balance — origin data, since no entry in the system derives it — and everything after that is computed from the ledger: `InitialBalance` + received `Inflows` into the account − received `Inflows` out of it − paid `ExpensePayments` whose `PaymentMethod` belongs to it, all of it **cut at the end of a month** (see the movement features below). A `CurrentBalance` cache column existed and was dropped (migration `20260827022816`): keeping it in sync would mean every route that touches money remembering to recalculate, and missing one doesn't break anything — it just drifts, and a plausible wrong balance is the worst failure this app has. The indexes for the computed read are already in place. Note transfers count **both** directions here, unlike the "how much came in" totals that exclude them.

`PaymentMethods` is the child of `Accounts` and is the single place where `pix`, `debit` and `credit_card` live — there is no separate cards table and no account of type `credit_card`. Creating an account auto-generates its `pix` and `debit` rows; credit cards are added by the user. Three columns are meaningful **only** on `Kind='credit_card'` and null everywhere else — `DueDay`, `ClosingDay` and `CompetenceMode` — and `PaymentMethodKind.section.ts` is the single place that enforces that, because Joi can see the `Kind` in the POST body but not the one already stored in a PUT.

**The card is described by two days of the month, and neither is derived from the other:** `DueDay` is the anchor of the installment chain, and `ClosingDay` (1–31) is the day the invoice closes — the two numbers the customer reads off the statement. The single inference is which month the closing belongs to: `ClosingDay > DueDay` closes in the month **before** the due month (closes 27, falls due on the 4th), `ClosingDay <= DueDay` closes and falls due in the same month. It replaced a slack in days (`ClosingOffsetDays`) in leva 9, because a slack that is right in August is off by a day in September — months have different sizes — and one day of drift on the closing becomes one month of drift in the cash-out. **`CompetenceMode` (`'invoice' | 'purchase'`, default `'purchase'`) says in which month a purchase on that card *weighs*** — see the movement features below. It governs `ExpensePayments.CompetenceDate` and nothing else; the balance never moves with it.

`Categories` covers **expenses only** for now, and `IdWorkspace` is `NOT NULL`: every category belongs to exactly one workspace, and every read is the plain `where(IdWorkspace = X)` that the rest of the schema uses. Until leva 9 the thirteen seeded categories were global rows (`IdWorkspace IS NULL`) shared by every tenant and read-only over HTTP — which made archiving and reordering them impossible to offer, because `Active` and `Position` on a shared row are everyone's. The migration copied them per workspace, repointed `Expenses.IdCategory` and `Budgets.IdCategory` to each tenant's own copy, and dropped the originals; creating a workspace now seeds the thirteen from `Categories.seed.ts`. The price, paid on purpose: fixing a seeded name is one `UPDATE` per workspace, not one `UPDATE`.

**A budget is a split of one month's income, and it lives in one table.** `BudgetPeriods` carries its own target — `IdCategory` and `IdPerson`, both nullable, with `CHECK (IdCategory IS NOT NULL OR IdPerson IS NOT NULL)`: at least one, possibly both. "250 for Tiago **in food**" is a single row, and it is exactly what the old `xor` CHECK forbade. The rows add up side by side — "Luana 250" plus "Luana + Mercado 100" is 350 for Luana, not a ceiling inside a ceiling — because the sum of every row is how much of the income has been allocated, which is the number that closes against what came in.

Until leva 9 this was template + instance: a `Budgets` table held a standing per-category ceiling ("mercado: 800/month, forever") and a routine froze it into the month on the 1st. That model was dropped whole, along with the table: a standing ceiling has nothing to say about "what does next month look like", the single target made the two axes independent, and nothing tied any of it to the income. **Nothing is materialized any more** — a month has a budget because somebody built it, and *any* month is readable and writable, past, current or future, which is what makes October buildable in September.

**Uniqueness is three partial unique indexes, one per target shape**, over `(IdWorkspace, ReferenceMonth, …)`. Three and not one because `NULL` never conflicts with `NULL` in a Postgres unique index: a plain `unique` over the four columns would happily take two `(no person, Mercado)` rows for the same month. It is the same device migration `20260905110000` already used, for the same reason.

**One routine is left, `CloseBudgetMonth.rotine.ts`**, and it is the only thing in the system that knows a month has ended. Its `ClosedAt` earned a second job: **a closed month refuses writes** (403 — the workspace and the role are fine, the month is not open), which is the lock that stops August being rewritten in November. Closing still filters `Status = 'open'`, so re-running never rewrites a `ClosedAt` — convergence is what makes the engine's catch-up safe. A month with **no rows at all** is not closed, so a past month nobody ever budgeted can still be built.

`GET /BudgetPeriods?ReferenceMonth=YYYY-MM` returns the month with `Spent` alongside each limit, because a ceiling with no spend next to it is a number nobody can act on. Three rules live in `BudgetPeriods/sections/BudgetSpent.section.ts`, and each one changes the answer: it sums **legs, not expenses** (600 in 6× costs the August budget 100, not 600 — the rest is next month's problem); the date that counts is the leg's `CompetenceDate`, which is when the spend *weighs*, never the `CashDate`; and it counts **pending together with paid**, unlike the account balance — a budget is what you have committed, a balance is what you have realized. Only canceled expenses drop out. The alert stays with the client: the response carries `LimitValue`, `Spent` and `AlertPercent`, and comparing three numbers is the caller's job.

**Each portion of spend consumes one budget row, or none** — the rule that keeps a split from double-counting itself. A *portion* is one leg crossed with one person of the split (`ExpensePersons.Value * ExpensePayments.Value / Expenses.TotalValue`); a leg nobody was charged for is one portion with a null person. A portion with person **P** and category **C** looks for `(P, C)`, then `(P, no category)`, and **stops there**; a portion with no person looks for `(no person, C)`. A portion with an owner never falls into a category-only row: Tiago's grocery spend does not eat the household's "Mercado". The two queries this replaced summed each axis independently, so 100 spent by Luana on groceries ate 100 of *her* row and 100 of *Mercado* — 200 out of a 1.000 split, for 100 spent. The price of the strict rule, written in the section: if every expense is stamped with a person, category-only rows never consume anything, and covering a person whole needs a row with **no** category — an allowance. The product doesn't paper over that; it shows it, as `Unbudgeted` in the response (the sum of the portions that matched nothing), which makes `sum(Spent) + Unbudgeted = the month's spend`. The matching itself runs in TypeScript over an in-memory index of the month's dozen rows, for the same reason `InvoiceDates` does: a money rule with three cases and a precedence is read and tested in one place, not spread across a `LATERAL` with an `ORDER BY`. `ReferenceMonth` is `YYYY-MM` here rather than the `From`/`To` of the movement lists, because a budget month really is a calendar month; `Utils.monthStart` normalizes it to the 1st, which is what makes the three partial indexes bite. `DELETE` on a period is a **physical** delete — the only one in the project — because a period is a plan, not a ledger entry: nothing points at it, no money passed through it, and "I don't want a grocery ceiling in September" is not history worth keeping.

`Persons` is who received or spent the money — the V3 `destinys` replacement. A person is just a name plus an **optional** `IdUser` link, so someone with no login (a child, a partner who doesn't use the app) can still take a share. Both split tables point at `Persons`, never at `Users` directly. Watch the column name: `IdUser` here is an **identity link**, not authorship — the opposite of what the same column means in `Accounts` and `Tags`. It is `unique` across the whole table, not per workspace, which is why no route accepts it from the client (guessing a sequential id would burn that user's only Person slot) and why a person carrying one **cannot be archived**: the link can never be rebuilt from a route, so archiving would drop that user out of every future split for good.

`Expenses` has **two independent split axes** that must never be conflated: `ExpensePayments` is the financial axis (one row per payment method *and per installment* — this is what moves balances), `ExpensePersons` is the analytical axis (who the cost is attributed to). Both split by absolute value, no percentages. Two payment methods and two people produce **2 + 2 rows, never 4**. `ClosingDate`/`DueDate` live on the leg, not the expense, because each installment falls in its own invoice; they're derived from the `PaymentMethods` `DueDay`/`ClosingDay` and are null outside `credit_card`.

**The leg carries two more dates, and they disagree on purpose** — both frozen at posting time, both written only by `InvoiceDates.section.ts`: `CompetenceDate` is **when the leg weighs** (budget, "what can I still spend"), and `CashDate` is **when the money leaves the account** (balance, statement), always `coalesce(DueDate, ExpenseDate)`. Outside a `purchase` card the two are identical, which is why they were one column until `CompetenceMode` existed. Confusing them is the failure this whole split exists to prevent: cutting the balance by competence would take an August purchase out of August's balance while the invoice only clears in September.

**Nothing is partially settled.** `Expenses.Status` is derived from the legs and only reaches `'paid'` once *every* leg is paid; `Inflows.Status` goes straight from `'pending'` to `'received'`. Neither table has a `PaidValue`/`ReceivedValue` column and neither has a `'partial'` state. The per-leg `Paid`/`PaidAt` on `ExpensePayments` stay because installments require them — a 6× purchase needs to know which parcels are settled — but that detail is never promoted to a partial status on the parent.

A recurring ("fixed") expense is a **chain of real occurrences**, not template + instances: every `Expenses` row is a real expense. The series root has a null `IdParentExpense` and carries `RecurrenceDay`/`RecurrenceEndDate`; generated occurrences point back at it. This is deliberate — a template row would be a phantom that every report has to filter out.

`Tags` are the temporary taxonomy (a trip, an event) alongside the permanent `Categories`: an expense has one category and N tags. The link table is `ExpenseTags` rather than a generic one so inflows can get their own later without touching `Tags`. `ExpenseTags`→`Tags` is `ON DELETE CASCADE`, so a physical delete would *succeed* and quietly strip the tag off every expense already marked — the `DELETE` route is `Active = false` for that reason, not because the database would refuse.

**A tag has no CRUD of its own — it is born with the expense.** The client sends `Tags` as **text**, and `Tags/sections/POST/resolveByName.ts` turns those strings into rows inside the expense's transaction: an existing name is reused (case-insensitively), an archived one is un-archived, a new one is inserted. So the feature has exactly two routes: `GET /Tags/search` (the suggestion input, ILIKE with the wildcards escaped, capped) and `DELETE`. There is no `POST` because registering a label before using it is two steps for one word, and no `PUT` because renaming a tag would relabel every expense already marked — whoever wants another name types another name on the next expense. That also makes reuse the un-archive path, which is why `Tags` no longer needs the name-check section `Persons` still has.

Both `Persons` and `Tags` carry `unique(IdWorkspace, Name)`, and **that index doesn't know about `Active`**: the archived row keeps its name occupied. Both features look the name up before writing — `PersonName.section.ts` to answer 406 instead of a 23505 as a 500 (the same shape as the free-email check at signup, index still the real guarantee), `resolveByName.ts` to reuse the row instead of inserting a second one. Both comparisons are deliberately *stricter* than the index: case-insensitive (`lower("Name")` in raw, identifier quoted), because "Maria" and "maria" in one split are a typo, not two people. The two differ in what they do with an archived row, and that follows from who names it: a person is a cadastro, so the name stays taken and a 406 says so — if that ever bites, the fix is a restore route; a tag is just typed text, so typing it again brings the row back, which is the only un-archive path either table has.

`Inflows` carries **both** money coming in and transfers between accounts, discriminated by `Kind`: `'inflow'` has a null `IdFromAccount` (the money came from outside) and `'transfer'` requires both accounts, different from each other — two `CHECK` constraints enforce this. Because a transfer is net-zero for net worth, **every "how much came in" total must filter `Kind <> 'transfer'`**, or the same money is counted again each time it moves between accounts. An inflow is description, value, `CompetenceDate`, `ExpectedDate`, the account it lands in and `Notes` — **and nothing else**: it has no category and no recurrence by design, and since batch 10 it has no split across `Persons` either. `InflowPersons` existed from the project's first migration and answered "whose money is this" back when the budget could not: until batch 9 the budget was a standing per-category ceiling. Batch 9 made `BudgetPeriods` carry a person and/or category target, so the budget **is** the split of the month's income — and keeping both meant two answers to one question that nothing forced to agree, with the inflow's split feeding no slice, no report and no comparison. The table was dropped (migration `20260923100000`); its mirror image on the expense side, `ExpensePersons`, stays exactly because it does feed something — `BudgetSpent` and the Dashboard's "by person" breakdown.

**Current scope.** The schema is complete — all 22 tables exist in `migrations/` (the 21 domain ones plus `RotineRuns`; two tables were born here and dropped again, `Budgets` in batch 9 and `InflowPersons` in batch 10, and they are gone from the count), and every domain table now has code on top of it: `Users`, `Workspaces`/`WorkspaceMembers`/`WorkspaceInvites`, `UsersAuth`/`TrustedDevices`, `Accounts`/`PaymentMethods`, `Categories`, `Persons`, `Tags`, `Inflows`, `Expenses`/`ExpensePayments`/`ExpensePersons`/`ExpenseTags` and `BudgetPeriods` — the last of these built by hand, with the monthly routine only closing the month that ended. On top of them sits `routes/Reports/`, which owns no table. **Workspace sharing is complete**: batch 2 delivered the invite and the join, and batch 6 closed it with member management — list, change role, remove, leave and transfer ownership, the five routes described under the session above. What is left without an API is only the platform tables: `UserDevices`, `Notifications`, `Plans`, `Subscriptions`.

`Accounts` is the first tenant-scoped feature, so it's the reference for the rest: `IdWorkspace` comes from the session token and every section opens with `WorkspacesAcessControl.assertMember`/`assertRole`, and every `getUnique` filters by `IdWorkspace` *as well as* the row id — the row id is sequential and arrives from the client, so a membership checked on your own tenant would otherwise let you read the neighbour's row. Both DELETEs are `Active = false` — `Inflows`→`Accounts` and `ExpensePayments`→`PaymentMethods` are `ON DELETE RESTRICT`, and the history has to keep pointing at the row that was actually used. **`InitialBalance` freezes once the account has movement** (`Accounts/sections/AccountMovement.section.ts`): with no cached balance there is nothing to recalculate, and moving the opening balance would rewrite last month's statement from underneath.

`Accounts` and `PaymentMethods` are two features, in `routes/Accounts/` and `routes/PaymentMethods/` — **one folder per table, no exceptions**, even when one table is the child of another. They lean on each other in both directions, always through an explicit cross-feature import: creating an account calls `PaymentMethods/sections/POST/createDefaults.ts` inside the account's own transaction (a `pix` and a `debit` row are the model's rule, not a convenience — an account with no payment method can't receive a single expense), archiving an account archives its methods, and `GET /Accounts` embeds them via `joinTables`. `POST /PaymentMethods` only takes `Kind='credit_card'`; `pix` and `debit` are never created by hand. Feature-owned Joi shapes stay with their feature and get imported — the account's response schema imports `paymentMethodResponse` from `PaymentMethods.schema.ts`, so the row is described once. Shapes that belong to no feature (`isoDate`, `color`) live in `Utils/joiSchemas.ts`.

`routes/Categories/` follows that reference with nothing special about it any more: `GET /Categories` returns one flat list, all of it owned by the workspace in the token. A fresh workspace is not empty — `POST /Workspaces` seeds the thirteen inside the same transaction that creates it, from `Categories.seed.ts` — which is what the old global rows were there to provide. Two rules carry the feature:

- **An id from another tenant is simply not found.** There is no ownership guard and no 406 of its own (`CategoryOwnership.section.ts` was deleted in leva 9 along with the global rows): a category the workspace doesn't own gets the same "não encontrada" as an id that never existed, which is the treatment every other feature gives a foreign id.
- **Archiving is `Active = false` on one row**, scoped by `IdWorkspace` in the `UPDATE` itself so a stray id can never reach another tenant's row. `DELETE` sets it and `PUT` takes `Active` to undo it — the same column, written by one feature, instead of a `restore` route that would have to agree with the other two about who may touch it. `GET /Categories?IncludeArchived=true` is what makes the archived row visible again: the same cut `GET /Expenses` uses for canceled rows, with the same meaning — absent hides, present shows everything. Restoring puts the row **last** (`max(Position) + 1`), because its old position belongs to somebody else by now and giving it back would tie two rows on `Position`.
- **Reordering is `PUT /Categories/reorder` with the whole list** of active ids, written as `Position = 1..N` in a transaction. Whole list, not "move id X to position N": the client already holds the order, and a partial write needs server-side renumbering — which is exactly where two people reordering at once leave two categories on the same `Position`. An id that is foreign, repeated, archived, or missing from the list is refused with 406 **before any write**, because a reorder that accepts an incomplete list is a reorder that duplicates `Position`.

**There is no hierarchy: a category is never the child of another** (migration `20260829010000_drop_categories_parent`). The column existed and was dropped along with everything it dragged behind it — checking that a client-supplied parent was visible to the workspace, refusing cycles (a cycle leaves the branch with no root, so it vanishes from the rendering while staying live and assignable by id), and cascading the archive down the subtree. None of that paid for itself with a dozen categories per workspace, and the flat list has no such failure modes.

#### PostgreSQL specifics

V3 was MySQL; V4 is PostgreSQL. Knex handles the DDL translation (`tinyint`→`smallint`, `.unsigned()` ignored, `enu`→`text`+`CHECK`, `binary`→`bytea`, `datetime`→`timestamptz`), but three things bite at the query layer:

- **`Active` is a real `boolean`.** Use `.where("Active", true)` / `.update({ Active: false })`. The MySQL habit of `.where("Active", 1)` throws `operator does not exist: boolean = integer`.
- **`numeric`, `bigint` and `date` are re-typed on read** by `registerPgTypeParsers` (`section/pgTypeParsers.ts`, called from `AppKnex.ts`). Without it node-postgres returns money and bigints as *strings* and `date` as a local-midnight `Date` that shifts the calendar day in UTC-3. Money and counters arrive as `number`; `date` columns (`CompetenceDate`, `DueDate`, `ReferenceMonth`, …) arrive as `"YYYY-MM-DD"` strings — they are calendar dates, not instants, so never wrap them in `new Date()` for display. Note the parsers are registered in the app path only; the Knex CLI (`knexfile.ts`) does not load them, which is fine as long as migrations only do DDL and inserts.
- **Identifiers are case-sensitive.** Knex always double-quotes, so the PascalCase table/column names work through the query builder. Any raw SQL must quote them explicitly (`select "IdUser" from "Users"`), or Postgres will fold to lowercase and fail.

Postgres has no `ON UPDATE CURRENT_TIMESTAMP`, so every model must set `UpdatedAt: KnexConnection.fn.now()` on update, as `Users.model.ts` does.

### The movement features

`routes/Inflows/` and `routes/Expenses/` + `routes/ExpensePayments/` are where money actually moves, and they share four rules that no earlier feature needed:

- **The period filter is `?From=YYYY-MM-DD&To=YYYY-MM-DD`, inclusive on both ends** (`periodQuery` in `Utils/joiSchemas.ts`), on `CompetenceDate` for inflows and `ExpenseDate` for expenses. A range, not `ReferenceMonth=YYYY-MM`: a month is expressible as a range, but a card invoice period — closing day to closing day — never lines up with the calendar month. Omit `Status` and the canceled rows stay out; ask for `Status=canceled` and they come back.
- **The balance is computed on every read** (`Accounts/sections/AccountBalance.section.ts`), embedded as `Balance` in `GET /Accounts`: opening balance + received inflows in − received transfers out − *paid* expense legs, the legs cut by `CashDate`. Pending is a forecast, not a balance. Three grouped queries for the whole list, never one per account. Two traps live in that one file: transfers count on **both** sides here (unlike "how much came in", which excludes `Kind='transfer'`), and the paid-legs query joins `Expenses` to skip canceled ones — canceling a settled expense is the refund, and without that join the money would stay out of the account forever.
- **The balance is always the balance *of a month*, cut at the last day of it.** `GET /Accounts?ReferenceMonth=YYYY-MM` (optional, defaults to the current month via `Utils.currentMonth`) recuts the `Balance`, never the list — the accounts are the same in any month. **State is not a date:** nothing stops a September inflow from being marked received, and with no cut that money would show up in August's balance — a plausible wrong balance, the worst failure this app has. The cut is half-open (`< the 1st of the next month`), like `BudgetSpent`, and it reads the *entry's* date — `CompetenceDate` on an inflow, **`CashDate`** on an expense leg — never `ReceivedAt`/`PaidAt`, which are the instant of the click: settling September's invoice today would otherwise put the cash-out in the wrong month. The opening balance obeys the same cut when `InitialBalanceDate` is set; a null date means the account always existed. Month here, not the `From`/`To` of the movement lists, because a balance is a *position*, not a slice — and it is what makes "how much did I have in July" answerable.
- **Money invariants are checked in cents** (`Utils.toCents`): `sum of parts === total` never holds in floating point. Every split closes exactly with the total, and the database enforces none of it.
- **Calendar math goes through moment, and never through a loose `Date`.** `date` columns are typed `CalendarDate` (a string) in `Utils/database.ts`, and `Utils.addMonthsToDate`/`setDayOfMonth` parse `"YYYY-MM-DD"` with moment in strict mode and format it back, so no instant ever escapes — in UTC-3 midnight on the 1st is the 31st of the month before. moment's `add` already clamps to the end of the month (31/01 + 1 month is 28/02); its `date()` does not, so `setDayOfMonth` clamps by hand. A `new Date()` in this path is now a compile error.

`Inflows` carries **both** kinds of money movement, and `InflowKind`/`InflowSplit` are the two sections that hold the rules the `CHECK` constraints only catch as a 500: an inflow has one account and a transfer has two different ones, and a transfer takes no split — nobody's share changed when money moved between your own accounts. Creation always lands `pending`; `POST .../receive` is what puts it into the balance, and it is all-or-nothing (no `partial`, no `ReceivedValue`). Editing a *received* inflow is allowed on purpose — that is what the no-cached-balance decision buys, since there is nothing to correct but the row itself. Both `PUT`s re-check the split against the **new** total even when the split wasn't sent, because when only the total moves it is the stored split that stops closing.

`Expenses` is one POST for three shapes — `single`, `installment`, `fixed` — and three rules carry it:

- **The two axes never mix.** `ExpenseAxes` validates them in separate passes and `GET` returns them as separate lists: two payment methods and two people are **2 + 2 rows, never 4**. Each axis closes with the total on its own. The category is required and checked by id (`ExpenseCategory.section.ts`); the tags arrive as **text** and are resolved by the `Tags` feature inside the same transaction, so an expense is the only thing that ever creates a tag.
- **`Status` is derived, in exactly one place** (`ExpenseStatus.section.ts`), recomputed inside the same transaction as any write to legs and never accepted in a body. It reaches `'paid'` only when *every* leg is paid, so settling 1 of 6 installments leaves the purchase `pending`, and an expense with no legs at all is never `paid` (`every` over an empty array is `true` — that guard is deliberate).
- **Payment dates live on the leg** (`InvoiceDates.section.ts`). On a credit card they are the invoice: buy on or before `ClosingDay` and it lands on this month's, after it and it is next month's — one integer comparison (`monthsToClosing`), with no rolling loop, because a closing day of the month can only ever be missed by one cycle. The due date rolls a month past the closing when `ClosingDay > DueDay` (`monthShift`). One day of difference in the purchase becomes one month of difference in the cash-out. Off the card there is no invoice, so `forPayment` returns nulls — but `forInstallment` still sets a `DueDate` one month apart per parcel, because **installments are not a credit-card privilege**: a store book, a `crediário` or splitting a purchase with a friend land on pix or debit and still have monthly parcels. The same file writes the leg's other two dates, and that is where the card's `CompetenceMode` is spent in a single line: `purchase` writes `ExpenseDate + (cycleShift + n−1) months`, so 600 in 6× still weighs 100 a month instead of 600 in the month of the purchase. The `cycleShift` is the same `monthsToClosing` the invoice dates use, and it is what makes the competence follow the **cycle** rather than the purchase date: on a card closing on the 30th, a purchase made on the 31st weighs in the *next* month, because the invoice that will charge it is the next one. The day of the purchase is kept and only the month moves — `addMonthsToDate` clamps 31/08 to 30/09 — because the Report's daily chart reads the competence as a day, and writing the closing date there would stack a whole month of purchases onto one spike. Off the card `cycleShift` is always 0 and the formula reduces to the one the `crediário` already used. `CashDate` ignores the mode entirely.

Installments are `Kind='installment'` with a **single** leg (any payment method — two legs would need a second axis inside the financial one to say which parcel came from where): 600 in 6× is six rows of 100 with their own invoice dates, `TotalValue` stays the purchase total, and the leftover cents go on the **first** parcel (`Installments.section.ts`) so the legs sum exactly to the total. A fixed expense is a chain of real occurrences — the root is the first one and carries `RecurrenceDay`/`RecurrenceEndDate`, and `Occurrences` (default 12) generates the window ahead so next month is already visible without a scheduler. Series edits (`PUT`/`DELETE .../series`) act on **the occurrence you called them on and every later one**, exactly like "this and following events" in a calendar: the cut is that occurrence's date, never the clock, which keeps "what was I paying in August" answerable and the behaviour verifiable in a test. `POST /ExpensePayments/.../pay` (and `unpay`, which exists because a wrong click otherwise takes money out for good) is the only thing that flips a leg, and it refreshes the derived status in the same transaction.

### Reports (`routes/Reports/`)

Two aggregate reads and one file download, over tables the feature does not own. It exists because **the aggregation rules contradict each other on purpose** — transfers count in the balance and not in "how much came in"; the budget counts pending and the balance does not; a spend is summed by leg, not by purchase — and while those rules lived replicated in the client, two implementations of the same question ended up showing two different totals on the same screen.

- **`GET /Reports/Month?ReferenceMonth=YYYY-MM`** is the Dashboard's two indicators, which disagree by design: `Available` ("what can I still spend") is the month being lived — competence dates, pending counts, and it **opens with `OpeningBalance`**, the realized balance at the end of the previous month; `CurrentBalance` ("what I have") is money that actually moved. `OpeningBalance` is not a new query: the balance cut is half-open, so `AccountBalance.getByAccounts(accounts, <1st of the requested month>)` *is* the closing balance of the month before. Overdue receivables and payables are added back on both sides and **exposed separately**, because a forecast that never arrives would otherwise inflate the indicator forever with nobody able to see why. The month's income comes back as three numbers, not one — `Inflows` (everything by competence) opened into `InflowsReceived` and `InflowsPending`, with `received + pending === Inflows` asserted in the test — because the budget screen asks "what came in, what is still coming, what is the total" and it must not answer by summing rows itself: the transfer cut and the canceled cut live here, and replicating them is how one question grows two totals.
- **`GET /Reports/Statement?ReferenceMonth=YYYY-MM`** is the statement, and it is **the balance opened line by line** — never a parallel query: `OpeningBalance` + the signed `Value`s = `ClosingBalance`, and that `ClosingBalance` is the same `Balance` that `GET /Accounts` returns for the month. The test asserts exactly that, in cents, and it is the only thing that notices the statement starting to drift from the balance. Two asymmetries carry it: the **account** statement holds only what settled (a pending line would break the sum), while the **card** statement is the invoice and therefore includes what is still unpaid; and card legs come **aggregated into one `invoice` line** on the account with the detail living on the card, because forty purchases are not forty lines on a bank statement. The card is cut by `DueDate` — an invoice is the pair `(card, due date)`, and on a `purchase` card the competence is the month the invoice *closes*, which on a card closing before its due month would split one invoice into pieces the issuer never charged.
- **`GET /Reports/Export?From=&To=`** is the **only route in the project that does not answer JSON** — an `.xlsx` written straight into `res` by `exceljs`, so `validateResponse` does not apply and the section receives the `res` itself. The `Gastos` sheet lists **legs**, like every other total here, and the summary sheet is built from **formulas** rather than numbers summed on the server: a spreadsheet exists to be edited, and deleting a row must not leave the total lying. Dates go out as `dd/MM/yyyy` **text**, because turning a calendar date into an Excel date would reintroduce the timezone the `pgTypeParsers` exist to remove.

### Mail (`Utils/Connections/Mailer.ts`, `Utils/Mail/`)

Three layers, and none of them knows the other two: the **transport** (`Utils/Connections/Mailer.ts` — SMTP, pool, timeouts, sender; zero domain) lives beside Knex because that is what it is, an external connection; the **message** (`Utils/Mail/templates/*.ts`) knows a "reset your password" email exists and what it needs; the **reason** is the section that has cause to send.

**Templates are centralized, unlike the Joi schemas, which stay with their feature.** The difference is that one Joi schema has nothing in common with another, while three emails share a layout — header, footer, colour, signature. That shared chrome is what decides where they live (`templates/layout.ts`).

**A template is a TypeScript module, never an `.html` file read at runtime.** `build:app` bundles `index.ts` into `build/bundle.js`, so a `readFile("templates/reset.html")` would look for a file nobody copied — the same trap that made migrations compile separately. And as code, `renderResetPassword({ Name, Link })` makes the compiler complain about a missing parameter; a `{{Link}}` nobody substituted reaches the user as `{{Link}}`.

- **`mailer.send({ to, subject, text, html? })` never throws.** A mail provider being down must not stop somebody from creating an account or asking for a password reset. It logs the failure and returns a boolean. One recipient per call, on purpose: `to: emails.join(", ")` would show every address to every recipient the first time somebody sends in bulk.
- **The transport is chosen before the envs are read**, and built lazily on the first send. In `NODE_ENV=test` the mailer uses nodemailer's `jsonTransport` and never looks at `MAIL_*` — nothing leaves over the network and the suite asserts the actual **content** with no mock, which is where email bugs live. Lazily, so a dev box with no SMTP configured still boots; a missing var then surfaces as a log line at send time instead of a boot that never happens.
- **Sending hangs off `attachOnEnd`** (`KnexTransaction`'s `TransactionEvents`) whenever the reason to send is a write: `fireOnEnd` runs *after* the transaction resolved, so a rollback sends nothing, and it swallows the error into `Logs.handleError`, so a dead SMTP cannot undo a signup. The caveat is real: `fireOnEnd` is awaited before the response, so SMTP latency lands in the request. That is accepted for the transactional emails this batch has — the user is on screen waiting for them — and it is why there is **no outbox and no queue**: a failure recovers by the user asking again. The criterion for that stopping to be enough is written down: an email the *system* fires on its own has nobody watching, and a failure in it is indistinguishable from "there was nothing to warn about"; that one needs persistence, and `Notifications` already has `ScheduledFor`, `SentAt` and the index the sweep would need.
- **`APP_URL` is the var that gets forgotten** (`Utils/Mail/appLink.ts`). The API does not know its own public URL, and every email here carries a link — without it somebody builds the link from the request `Host`, and a forged `Host` turns into a password-reset link pointing at somebody else's server. **The link points at the front, never at the API**, so the email never becomes a `GET` that changes state.
- **The mailer never logs the body.** The `text` of a reset email contains the token; `Logs` records that an email went out, to whom, with what subject — same rule as `Utils.redactSensitive` over `req.body`.
- **Deliverability is not code.** Sending as `@gastosmensais.com.br` through an SMTP not authorized in SPF/DKIM lands in spam, and no architecture fixes that.

### Routines (`rotines/`)

`rotines/` sits at the repo root **next to `routes/`**, because it is the second family of entry points: an HTTP request and an elapsed schedule are the two things that make code here run. `rotines/index.ts` exports a `Rotines` array — the list, and nothing more — exactly like `routes/index.ts` exports `Routes`; it holds the two budget routines that run on the 1st, one opening the new month and one closing the old. The spelling is `rotine`, not `routine`, to match `Logs/rotines/` and `logFlags.rotine`, which have been written that way since V3.

**The tick asks what came due; the database decides who runs.** Every minute the engine (`section/RotineEngine.ts`) computes each routine's last due occurrence and tries to insert `RotineRuns { Name, ScheduledFor }` with `onConflict().ignore()`; only the writer that won runs, and it stamps `FinishedAt`/`Status`/`Error` at the end. `unique(Name, ScheduledFor)` buys three things at once: **catch-up** for free (server down on the 1st and up on the 2nd — the last due occurrence is *still* the 1st, nobody claimed it, it runs, with no recovery logic anywhere), **idempotency** across restarts and instances, and a queryable execution history. A `setInterval` of the period would have had none of them: it drifts from the boot instant, resets on every deploy, and silently skips a month.

The schedule is declarative and typed (`{ kind: "monthly", day: 1, hour: 3 }`), not a cron string — the compiler checks the first and nobody checks the second. `lastDueOccurrence(schedule, now)` is a **pure string→string function** over `"YYYY-MM-DD HH:mm"` labels, which is what makes "1 March at 3am" testable without waiting for March; `ScheduledFor` is stored as that same string, so no timezone conversion can turn one occurrence into two rows.

Four rules hold for every routine here:

- **It claims only the most recent occurrence, never a backlog.** Five days down do not fire five daily runs. A routine is *convergent* — running it again lands on the same state — and that is what makes catch-up safe. The day one of them needs to process every missed occurrence, it is not a routine, it is a queue.
- **It runs as the system, and `assertMember` does not apply.** `runForEachWorkspace` (`section/WorkspaceRunner.ts`) iterates the tenants itself and passes `IdWorkspace` straight to the sections, below the access layer. The real risk is not the routine breaking — it is somebody *loosening* `assertMember` to accept a null actor, which would open a hole in the routes.
- **One transaction per workspace, not per tick.** One workspace with bad data cannot leave the other five hundred without their month. Each unit fails alone, is logged, and the failures surface together at the end so the run is recorded as `failed` with the list in `Error`.
- **It delegates, never reimplements.** A routine is a third caller beside the controller and the test.

`RotineRuns` is the **first table with no `IdWorkspace`** — deliberate: it is a system table, and one execution crosses every workspace. There is no `Rotines` table either; the catalogue is code, since a catalogue in the database could disable a routine the code still believes exists. Turning one on or off is editing that list, and the log switch comes from `Utils/logFlags.ts`, as everywhere else.

**`stop()` waits for the tick in flight**, it doesn't just clear the `setInterval` — a tick that has already claimed its `RotineRuns` row and hasn't stamped the `FinishedAt` yet is exactly the orphan the unique index makes unrecoverable. It is the first step of the shutdown below, and `Rotines.test.ts` holds a routine open on a promise to prove the wait is real.

Two operational notes: the engine is started **only from `index.ts`, and only outside `NODE_ENV=test`** — a routine firing mid-suite would change the database under a running test — the same failure mode the cache's telemetry timer used to cause before the whole subsystem was deleted. And `moment` with no timezone uses the server clock, so the process needs `TZ=America/Sao_Paulo`: in UTC a "1st at 00:30" routine fires at 21:30 on the 31st in Brazil and materializes the wrong month. There is deliberately **no manual trigger** (no route, no CLI entry point): routines are convergent and catch-up already covers an outage, so the answer in production is to wait for the next tick.

### There is no socket and no in-memory cache

Both existed, both came from another project, and both were deleted whole — the API listens on **one** port, `PORT`, and nothing else.

The socket.io server ran on a `SOCKETPORT` of its own with `cors: { origin: "*" }`, and it booted **on import**, which is why the test env had to hand it an ephemeral port. On top of it sat `routes/Cache/` — an in-memory bucket store exposed as `GET /Cache/CacheName=:CacheName`, `POST /Cache` and `POST /Cache/Reset/...`, **not scoped by workspace**: any logged-in account wrote unbounded data into the server's memory and read back what other tenants had put there. `GET /Utils/Reload` went with them; it broadcast a `reload` to every connected client and any authenticated user could press it. No screen ever consumed any of the three.

Two consequences worth keeping in mind: a bucket store reachable over HTTP is not where a server-side guard belongs (see `MailCooldown.section.ts`, whose window is a private `Map` for exactly that reason), and anything that wants to push to the browser now starts from nothing — which is the right place to start it, next to the HTTP server rather than on a second port.

### Shutdown

`SIGTERM` — what `docker stop` sends, ten seconds before the `SIGKILL` — and `SIGINT` (Ctrl+C) are handled in `index.ts`, and until batch 7 neither was: the process died where it stood. Three things were cut in the middle of those ten seconds — a request in flight, including one inside a transaction; the Knex pool, which without `destroy()` leaves connections hanging on the Postgres side until *its* timeout; and the routine tick, which is the expensive one. An occurrence claimed in `RotineRuns` and interrupted before its `FinishedAt` is **never claimed again** — that is what `unique(Name, ScheduledFor)` guarantees — so the month never closes, and catch-up, which exists precisely to cover an outage, does not cover this one.

The order is the whole design: each step exists so the next one has nothing new to wait for.

1. **`rotineEngine.stop()`** — no new tick starts, and the one already running is *awaited*. Stopping the `setInterval` without waiting is the same interruption under another name.
2. **`httpServer.close()`** — stops accepting connections and waits for the requests in flight. **One** server, since the socket was deleted (see above); with it there would be a second port to close, and a `close()` that forgets the other is a process that never dies.
3. **`KnexConnection.destroy()`** — after the server, never before: closing the pool first leaves the in-flight request with no connection, which is the same cut inside a transaction with another name.
4. **A ten-second ceiling**, then `process.exit(1)`. A shutdown that hangs is worse than an abrupt one — the `SIGKILL` lands in the same place ten seconds later, with no log and nobody knowing what held it. The timer is deliberately not `unref`ed: it is what keeps the process alive until one of the two exits happens, and it's cleared on the happy path.

**`closeIdleConnections()` is what makes step 2 actually end**, and it runs on a 200ms sweep rather than once. nginx holds idle keep-alive connections to the upstream, and an idle connection is not a request in flight — but the connection that *carried* the in-flight request isn't idle at the instant of `close()`: it goes idle when the response leaves, by which time a single call has already happened. Measured, that left the shutdown hanging on that socket for three seconds, until the client gave up by itself.

The second signal is ignored while the first is being served — a second `destroy()` on the pool while the first is still waiting for the server. And **the orphan occurrence from before this existed stays orphaned**: routines are convergent and the next month reprocesses. What the handler prevents is new ones.

### Logging

Winston. `Logs.insertLog(log, type)` writes one event of a `type` (∈ `info`/`error`/`userError`/`untracked`/`telemetry`); `insertRotineLog` writes under the routine's name. `Logs.handleError` auto-classifies a thrown `APIError` with `status === 406` as `userError`, everything else as `error`.

**Where the event goes is decided by the environment; what is in it is not** (`createLogger`, `Utils/Logs.ts`). Outside production it is the daily-rotate-file of always — `Logs/<type>/<date>.<type>.log`, `Logs/rotines/<name>/`, seven days kept — because `Logs/` on a development machine is useful and costs nothing. **In production the transport is `Console`**: in a container a file on disk is the image's write layer, so the log vanishes on the next `docker compose up`, which is exactly when somebody wants to read what happened before; the path depended on `process.cwd()`, which moves with the `WORKDIR`; and `maxFiles: 7` has nobody to honour it if nobody ever reads the volume. stdout is what Docker's log driver captures, and rotation and a size ceiling become the orchestrator's configuration — outside the application, which is where that decision belongs. The environment is asked through `isProduction()` and nothing else, and asked **inside** `createLogger` — which runs lazily, at the first log of each type — so in production the `DailyRotateFile` is never constructed, and constructing it is what would create the `Logs/` directory nobody is going to read. The JSON keys are the same on both sides (`level`, `timestamp`, `message`); the one difference is indentation, and it isn't cosmetic: a log driver reads **one line per event**, so the indented JSON that is comfortable in a file would become a dozen loose records with no level and no timestamp in stdout.

## Integration tests

There are no unit tests: every suite is an integration test that goes through the real pipeline (`AsyncHandler` → Joi schema → section → Knex → Postgres). Nothing is mocked.

- **One file per feature/table**, next to the feature: `routes/<Feature>/<Feature>.test.ts` (`testMatch: **/*.test.ts`). `routes/Users/Users.test.ts` is the reference. Inside it, **one `describe` per route**, in the same order as `<Feature>.route.ts`, plus a final `describe("Fluxo end to end")` that walks the feature's happy path over HTTP only.
- **Helpers live in `Utils/Tests/`** (barrel at `Utils/Tests/index.ts`): `TestClient`, `TestDatabase`, `TestEnv` and the factories in `section/factories/`.
- **`TestClient`** is the HTTP client. By default supertest boots the app in-process; with `TEST_BASE_URL` set the exact same tests hit a running server (end to end mode) — that's why tests must never call sections/models directly. It sends the token as the `token` cookie — the same and only channel the browser uses — and `client.login(email, password)` authenticates through the real route and picks the token out of the `Set-Cookie` it gets back. The token is the whole session, so the client holds nothing else; to build a session the login can't produce — no workspace selected, or one pointing at someone else's — use `UsersFactory.buildToken(IdUser, IdWorkspace?)`, which is how the suites prove `assertMember` still catches a genuinely signed token whose membership doesn't exist.
- **`TestDatabase`** wraps the test connection: `truncate([...])` (per suite, CASCADE + restart identity), `connection()` for asserting the persisted row, `reset()`/`migrate()`. Every destructive helper goes through `TestEnv.assertTestDatabase()`, which refuses to run unless the database name contains `test` (override with `TEST_DB_UNSAFE=true`). **`truncate(["Users"])` cascades through `Workspaces` into `Categories`, and that empties the whole table — the 13 global rows from the seed migration included, since they live there with a null `IdWorkspace`.** `globalSetup` only re-runs the migrations once per execution, so the first suite to truncate takes the seed away from every suite after it: a suite that needs a global category seeds its own (`Categories.test.ts` does) instead of relying on the migration.
- **Factories** seed direct to the DB (`UsersFactory.create()` returns the row, its workspace, its own `Persons` row, the plaintext password and a valid JWT; `UsersAuthFactory.create(IdUser)` seeds a passkey row). Use them for arranging state; use HTTP for what is under test. `UsersFactory` seeds the workspace, the membership and the owner's person because signup does — each of those is a state the app can't reach without, and seeding one the app never produces would hide the bug instead of finding it.
- **Known gap:** no suite closes the WebAuthn loop, because `register`/`authenticate` need a signature from a real authenticator. `UsersAuth.test.ts` covers everything on either side of the crypto — challenge issuing and binding, who may call what, device state, persistence — and every rejection path. The factory's public key is random, so those credentials list and expire correctly but can never verify.
- **Config**: `Utils/Tests/globalSetup.ts` rolls back and re-runs the migrations once per execution (so the migration seeds are always there); `setupFiles` loads `Utils/Tests/section/TestEnv.ts` before any app module, since `enviromentManager`/`AppKnex` read the env at import time; `setupFilesAfterEnv` destroys the Knex pool at the end of each file. `maxWorkers: 1` because all suites share one database, and `forceExit: true` because importing the app can still leave a handle the suite doesn't own (the nodemailer pool). `setupSuite.ts` is now only that `disconnect`: it also used to stop the cache's telemetry interval — a timer that fired once a minute and, landing after Jest tore an environment down, surfaced as a winston crash **inside whatever test was running next**. The subsystem that owned it is gone, and so is the workaround.
- **`.env.test`** (gitignored, template in `exemple.env.test`) is layered *on top of* `.env` with `override: true` — it only declares what changes in tests (`PORT`, `DB_SCHEMA` pointing at `gastos_mensais_v4_test`, optional `TEST_BASE_URL`).

```
npm test                # app em memória (supertest)

npm run start:test      # terminal 1: servidor apontando para o banco de teste
npm run test:e2e        # terminal 2: mesmas suítes, servidor real
```

`Utils.configEnv()` applies the same `.env` + `.env.test` layering, so the server started with `NODE_ENV=test` and the test process read the identical config — without that the factories would seed one database while the server reads another.
