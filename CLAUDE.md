# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm start` — run the API in dev mode via nodemon (`tsx index.ts`, restarts on `.ts`/`.js` changes, ignores `Logs/*`).
- `npm test` — run the integration suite (Jest in-band, config in `jest.config.ts`); `npm test -- Users` filters by file. `npm run test:watch` re-runs on change. See "Integration tests" below.
- `npm run start:test` + `npm run test:e2e` — the end to end pair: the first boots the API with `NODE_ENV=test` (test database, port 4100), the second points the same suites at it via `TEST_BASE_URL`. Both go through `cross-env`, since `VAR=value cmd` doesn't work in the Windows shell npm uses.
- `npm run build` — full build: `build:app` (webpack bundles `index.ts` → `build/bundle.js`, `node_modules` excluded via `webpack-node-externals`) + `build:migrations` (`tsc -p tsconfig.migrations.json` compiles `migrations/*.ts` → `build/migrations`, compiled independently of the app bundle since migrations run through the Knex CLI).
- Migrations (Knex CLI, `development` environment only, config in `knexfile.ts`): `npx knex migrate:latest`, `npx knex migrate:rollback`, `npx knex migrate:make <name>`.
- No lint script is configured.

## Environment

- Env vars load through `Utils.configEnv()` (`Utils/Utils.ts`), which reads `.env`, or `.env.test` when `NODE_ENV=test`. `exemple.env` documents the full var list (`PORT`, `SOCKETPORT`, `DB_CLIENT`, `DB_HOST`, `DB_LOGIN`, `DB_PASSWORD`, `DB_SCHEMA`, `DB_PORT`, `JWT_SECRET`, `CONSTANTS_PATH`, `WEBAUTHN_RP_ID`, `WEBAUTHN_RP_NAME`, `WEBAUTHN_ORIGIN`).
- All env access goes through `enviromentManager.getEnv(key, optional?)` (`Utils/enviromentManager.ts`), never `process.env` directly. Values are read as-is from the `.env`; a missing var throws an `APIError` at boot unless `optional` is `true`, in which case it returns `""`. The `.env` itself is what protects the secrets, so keep it out of git and restrict its file permissions — there used to be an AES layer here with the key hardcoded in the repo, which is why it was removed rather than fixed.
- `Utils.getConstants()` reads a JSON file for runtime-tunable flags, path from `CONSTANTS_PATH` (default `Utils/constants.json`). The `Constants` interface in `Utils/Utils.ts` only types a subset of the fields actually present in `constants.json` — extra keys are unused leftovers from a template and can be ignored.

## Architecture

Express + TypeScript API using Knex over PostgreSQL (client is configurable via `DB_CLIENT`). Path alias `root/*` maps to the repo root — used everywhere instead of relative imports across features (wired via `tsconfig-paths/register` for `ts-node`/`tsx`, and `TsconfigPathsPlugin` for webpack).

### Feature module layout

Each feature lives under `routes/<Feature>/` (see `routes/Users/`, `routes/Workspaces/`, `routes/UsersAuth/`, `routes/Cache/`, `routes/Utils/`) with a consistent split:

- `<Feature>.route.ts` — an `express()` sub-app with route definitions; every handler is wrapped in `AsyncHandler`, often preceded by a schema validator. All sub-apps are collected into the `Routes` array in `routes/index.ts` and mounted via `server.app.use(Routes)`.
- `<Feature>.controller.ts` — thin: pulls params/body off `req`/`res.locals`, delegates to a class in `sections/`, calls `res.json(...)`.
- `<Feature>.schema.ts` — Joi schemas wrapped by `joiController` (`Utils/joiController.ts`): `validateBody`/`validateParams`/`validateQuery`/`validateResponse`. Each returns middleware built from `AsyncHandler(fn, requireToken=false)`, so schema validation itself never requires auth even when the route does.
- `<Feature>.model.ts` — a `class_X_model extends BaseModel` (`Utils/Base.ts`) exposing the injected `KnexConnection` as `this.KnexConnection`; holds the Knex queries for one primary table. One model file per table, always.

**A table that has routes of its own gets its own feature folder** — `routes/Accounts/` and `routes/PaymentMethods/` are separate even though the payment method is the child of the account. A table with no routes of its own stays a second model file inside its parent's folder (`Workspaces/WorkspaceMembers.model.ts`, `UsersAuth/TrustedDevices.model.ts`): it's reached only through the parent's sections, so it has nothing to put in a route/controller/schema. Cross-feature calls go through the `root/*` alias, never a relative path out of the folder.
- `sections/` — business logic, one class per operation (e.g. `GET/getSelf.ts`, `POST/create.ts`), each with a `run()` method the controller calls; plus feature-local support files like `AcessControl.section.ts` and a `types.ts` namespace for payload types.

Follow this same file split (route/controller/schema/model/sections) when adding a new feature or endpoint rather than putting logic directly in the controller.

### Request pipeline

`AsyncHandler` (`Utils/AsyncHandler.ts`) wraps every route handler and is the single place that: loads constants, enforces auth (calls `Users_controller.acessMiddleware` unless `requireToken` is explicitly `false`), awaits the handler, and catches errors — logging via `Logs.handleError` (gated by `constants.logs.routeErros`), replying with `{ msg }` + `error.status` for a thrown `APIError` (`Utils/Logs.ts`), or a bare 500 otherwise.

Auth is JWT-based (`routes/Users/sections/AcessControl.section.ts`): `acessMiddleware` reads the token from the **httpOnly `token` cookie — and only from there** — verifies it with `JWT_SECRET`, and sets `res.locals.IdUser` and `res.locals.IdWorkspace` on success (typed via the `Express.Locals` augmentation in `Utils/Globals.d.ts`). `cookie-parser` is mounted in `Utils/server.ts` for exactly this: express writes cookies (`res.cookie`) but does not read them, so without it `req.cookies` is undefined and every protected route answers 401.

**There is no `authorization` header path, deliberately.** Two ways in means the weaker one decides, and a header accepted from anywhere escapes the `sameSite: 'strict'` that is the whole CSRF defense now that the browser attaches the credential by itself. `Users.test.ts` locks this in: a perfectly valid token sent in the header is a 401. The cookie's three attributes carry the session's security and are asserted, not assumed — `HttpOnly` (an XSS cannot read the token), `SameSite=Strict` (the browser never attaches it to a cross-site request; CORS would not help, since CORS governs who reads the response, not who sends the request), `Max-Age=86400` (dies with the token).

**Deployment assumes same origin.** The front-end is served from `www.gastosmensais.com.br` and the API from `www.gastosmensais.com.br/api` behind nginx: same scheme, host and port, so the browser never treats these as cross-origin — no CORS, no preflight, and the cookie rides along. `cors()` stays mounted but is inert in that setup. In development, front and API on different ports **are** different origins, which `sameSite: strict` blocks: proxy `/api` through the dev server (Vite `server.proxy`) so dev matches production instead of loosening the cookie. And `NODE_ENV` must actually be `production` at deploy, or `secure` is never set on the cookie.

Every login ends at `AcessControl.startSession(res, IdUser)` — it resolves the default workspace, issues the token carrying both ids, and stamps `LastLogin`. Both credential paths (password and biometrics) call it and nothing else emits a token, so the two can't drift apart in what they record.

Signup (`POST /Users`) creates the **user, their workspace and their own `Persons` row in one transaction** (`routes/Users/sections/POST/create.ts` + `routes/Workspaces/sections/POST/create.ts` + `routes/Persons/sections/POST/createSelf.ts`) and returns `{ IdUser, IdWorkspace }`. Every domain table is scoped by `IdWorkspace`, so a user without one can't record anything — half an account. The workspace also gets its `WorkspaceMembers` row in the same transaction: reads go through membership (`Workspaces_model.getByMember`), so a workspace without it is an orphan tenant nobody can see. And every split is between `Persons`, never `Users`, so without that row the owner couldn't appear in their own split — `createSelf` is the **only** writer of a person's `IdUser`, and the value comes from the user just inserted, never from the body. It is skipped (not renamed, not refused) when the name is already taken in a workspace being joined, since `unique(IdWorkspace, Name)` would otherwise let a namesake bring the whole signup down. There is no `POST /Workspaces`; today the only way a workspace is born is signup.

**The session is two things — who you are (`IdUser`) and which workspace you're in (`IdWorkspace`) — and both ride inside the same signed token.** `acessMiddleware` reads the token once and puts both on `res.locals` (typed in `Utils/Globals.d.ts`). `POST /Workspaces/switch` is the only route that takes an `IdWorkspace` written by the client; it checks membership and then **re-issues the token**, because the token is what carries the selection. `AcessControl.startSession` selects the user's first workspace on every login (`SelectDefault`), so a session never starts without one and `switch` really is a switch.

The token is **signed, not encrypted** — a JWT payload is base64, so anyone holding it reads `IdUser` and `IdWorkspace` in the clear. Never put a secret in there. What the signature buys is the thing that matters here: the client cannot swap the workspace for another one. What it buys over a second cookie of its own: a separate `IdWorkspace` cookie would be client data, rewritable to any sequential id — inside the signed token that door is shut, and the whole session lives and dies as one cookie.

**Signed is not the same as still true, so `assertMember` stays.** The token is a snapshot of the authorization taken at login and it lives 24h: membership can be revoked, or a role downgraded, after it was issued. Authentication the token settles; authorization only the database can answer. So every tenant-scoped section still starts with `WorkspacesAcessControl.assertMember`/`assertRole` (`routes/Workspaces/sections/AcessControl.section.ts`) — and note 7 of the 9 call sites are `assertRole`, which needs the *current* role and would have to hit the database regardless. Those return the **membership row**, and sections use the `IdWorkspace` that comes back from it — never the one that arrived, which is named `SelectedIdWorkspace` in every signature precisely so a stale value can't reach a query by accident. A token with no workspace answers 406 "Nenhum workspace selecionado" (the fix is `switch`); not-a-member answers 406 "not found", not 404 — a 404 would confirm the workspace exists.

`AcessControl` owns the cookie: `setTokenCookie` writes it (login, and `switch` when it reissues the token), `clearTokenCookie` drops it. Nothing else emits a session.

### Biometrics (WebAuthn), `routes/UsersAuth/`

Passkey login, carried over from V3's `webAuth` (`@simplewebauthn/server` v13). Two two-step flows — ask for options, return the signed assertion — stitched together by a `ChallengeToken`:

- **The challenge is a short JWT, not a session.** V3 parked it in a server-side session; here the API keeps no state between the two steps, so `WebAuthnChallenge` signs `{ challenge, type, IdUser? }` with `JWT_SECRET` for 5 minutes and the client returns it in the POST body. Signing rather than echoing is the whole point: a client-chosen challenge isn't random and opens replay. `type` lives inside the token so a register challenge can't be spent as a login one, and `register` additionally checks `challenge.IdUser` against the token's user, or a challenge lifted from another account would pin a passkey on the wrong one.
- **`DeviceKey` is not a credential** — it's a 32-byte base64url id the API generates and the device stores. It only answers "which credentials to offer here" and "have I already asked about biometrics on this device". Authentication is the passkey signature, nothing else. base64url (not V3's base64) because it travels as a URL param.
- **The user is resolved from the credential, not the device.** Login options take a `DeviceKey` and may return several `allowCredentials` (two people can enrol on one phone); `authenticate` looks up the `CredentialId` that came back signed. `Counter` is written back on every login — that's what keeps the lib's clone detection working.
- **`checkDevice` is tri-state**, like V3's `checkUser`: `true` = passkey here, `false` = the user declined here (`TrustedDevices`, V3's `ignoreauth`, written by `skipDevice`), `null` = never asked. Registering clears the decline.
- Public routes are exactly the ones a device without a token needs: `checkDevice`, login options, `authenticate`. Enrolling and removing credentials require a password session.
- Removal is a soft delete: the row stays so its `CredentialId` keeps the unique index occupied, otherwise an authenticator still holding the passkey could re-register it as new.

Passwords are hashed server-side and only there: `PasswordHasher` (`routes/Users/sections/PasswordHasher.section.ts`, bcrypt cost 12) is the single place that hashes and compares, used by `create`, `update`, `updatePassword` and `validateLogin`. The client sends the plaintext password in the **body** — never in the URL, since the path reaches the proxy access log, the browser history, the `Referer` header and `Logs.handleError` via `req.originalUrl`; that's why `POST /Users/login` and `PUT /Users/updatePassword` take a body instead of route params. `AsyncHandler` runs `Utils.redactSensitive` over `req.body` before logging, and `getSelf` strips `Password` from the response. Don't pre-hash or encrypt the password on the client: whatever the API receives becomes the effective credential, so a leaked hash could be replayed as-is.

### Database (Knex)

- `Utils/Connections/Knex/KnexConnection.ts` builds the shared `KnexConnection` from the `DB_*` env vars, and exports `KnexTransaction(fn)` — wraps `knex.transaction`, passing a `TransactionEvents` (`section/transactionEvents.ts`) so code inside a transaction can register `attachOnEnd(fn)` callbacks that fire after the transaction resolves. Models return QueryBuilders, so a section running inside a transaction enlists each query with `.transacting(tx)` (see `routes/Users/sections/POST/create.ts`) instead of building a second set of models.
- `DBTypes` (same file) maps table name → row interface. Row shapes themselves live in `Utils/database.ts` under the `Database` namespace. When adding a table, add its interface to `Database` and register it in `DBTypes` — this is what gives `joinTables` its type safety.
- Two custom QueryBuilder methods are registered globally in `Utils/Connections/Knex/AppKnex.ts`:
  - `.joinTables({ tableName: { selfPath, destinyColumn?, type?: "single"|"multi", append? } })` (`section/JoinTables.ts`) — fetches related rows from another table and attaches them onto the result (single object or array), based on `DBTypes`. Use `append` to further filter/shape the sub-query. It applies **no implicit filter**: only the registration tables carry `Active` (see below), and filtering it is each model's job via `append: (q) => q.where("Active", true)`. The name is `joinTables` (not `join`) because Knex's `.join()` is native and `QueryBuilder.extend` throws at boot on a name collision.
  - `.returnId(idColumnName)` (`section/returnId.ts`) — only valid on a single-row insert; returns the inserted id, branching on `DB_CLIENT` (mysql/mysql2 uses the insert id, other clients use `.returning("*")`).

#### Schema conventions

Tables are PascalCase plural, PK is `Id<Singular>` via `table.increments(...)`. Money is always `decimal(15,2)`, never float. Every table has `CreatedAt` and `UpdatedAt`; there is no `ON UPDATE` in Postgres, so every model sets `UpdatedAt` itself.

`Active` means soft-delete/archive and exists on every registration table: `Users`, `UsersAuth`, `TrustedDevices`, `Accounts`, `PaymentMethods`, `Categories`, `Budgets`. Elsewhere the lifecycle comes from a `Status` column or the row cascades from its parent.

Domain tables are scoped by `IdWorkspace` (tenant) with `IdUser` as author. One workspace per user today; `WorkspaceMembers` is already in place for sharing later.

**An account has no stored balance.** `Accounts.InitialBalance`/`InitialBalanceDate` are the opening balance — origin data, since no entry in the system derives it — and everything after that is computed from the ledger: `InitialBalance` + received `Inflows` into the account − received `Inflows` out of it − paid `ExpensePayments` whose `PaymentMethod` belongs to it. A `CurrentBalance` cache column existed and was dropped (migration `20260827022816`): keeping it in sync would mean every route that touches money remembering to recalculate, and missing one doesn't break anything — it just drifts, and a plausible wrong balance is the worst failure this app has. The indexes for the computed read are already in place. Note transfers count **both** directions here, unlike the "how much came in" totals that exclude them.

`PaymentMethods` is the child of `Accounts` and is the single place where `pix`, `debit` and `credit_card` live — there is no separate cards table and no account of type `credit_card`. Creating an account auto-generates its `pix` and `debit` rows; credit cards are added by the user. `ClosingDay`/`DueDay` are only meaningful on `Kind='credit_card'`.

`Categories` covers **expenses only** for now, and `IdWorkspace IS NULL` marks a system-wide predefined category — every read is `where(IdWorkspace = X or IdWorkspace is null)`, with the `or` inside a grouped callback so it can't escape the `Active` filter. Those global rows belong to no tenant and are the *same row* for everyone, so they are **read-only over HTTP**: they show up in every workspace's list and no route may write them.

Budgets are template + instance: `Budgets` holds the standing limit for a category (one row per category, no month), and `BudgetPeriods` holds one frozen row per month. Editing `Budgets` changes the future only — past periods keep the limit that actually applied, which is what makes "what was my limit in March" answerable. Never read a past month's limit off `Budgets`.

**The monthly routine does not exist yet, so the period rows are created by hand**, and `routes/Budgets/` is shaped around that: `POST /Budgets` takes `{ IdCategory, ReferenceMonth, LimitValue }` and writes both rows in one transaction — it resolves the standing definition (creating it, or updating it to the new limit, since `unique(IdWorkspace, IdCategory)` means there is only ever one) and then materializes that month. The second write lives in `BudgetPeriods/sections/POST/createForMonth.ts` precisely so the routine can call it unchanged later, with the current month instead of a user-supplied one. `Budgets.Active` ("stop budgeting this category") is the one thing nothing reads yet — it only starts mattering when the routine does.

`GET /Budgets?ReferenceMonth=YYYY-MM` returns the month with `Spent` alongside each limit, because a ceiling with no spend next to it is a number nobody can act on. Three rules live in `Budgets/sections/BudgetSpent.section.ts`, and each one changes the answer: it sums **legs, not expenses** (600 in 6× costs the August budget 100, not 600 — the rest is next month's problem); the date that counts is `coalesce(DueDate, ExpenseDate)`, so a card purchase lands on the month its invoice falls due; and it counts **pending together with paid**, unlike the account balance — a budget is what you have committed, a balance is what you have realized. Only canceled expenses drop out. The alert stays with the client: the response carries `LimitValue`, `Spent` and `AlertPercent`, and comparing three numbers is the caller's job. `ReferenceMonth` is `YYYY-MM` here rather than the `From`/`To` of the movement lists, because a budget month really is a calendar month; `Utils.monthStart` normalizes it to the 1st, which is what makes `unique(IdBudget, ReferenceMonth)` bite. `DELETE` on a period is a **physical** delete — the only one in the project — because a period is a plan, not a ledger entry: nothing points at it, no money passed through it, and "I don't want a grocery ceiling in September" is not history worth keeping. The definition survives it.

`Persons` is who received or spent the money — the V3 `destinys` replacement. A person is just a name plus an **optional** `IdUser` link, so someone with no login (a child, a partner who doesn't use the app) can still take a share. Both split tables point at `Persons`, never at `Users` directly. Watch the column name: `IdUser` here is an **identity link**, not authorship — the opposite of what the same column means in `Accounts` and `Tags`. It is `unique` across the whole table, not per workspace, which is why no route accepts it from the client (guessing a sequential id would burn that user's only Person slot) and why a person carrying one **cannot be archived**: the link can never be rebuilt from a route, so archiving would drop that user out of every future split for good.

`Expenses` has **two independent split axes** that must never be conflated: `ExpensePayments` is the financial axis (one row per payment method *and per installment* — this is what moves balances), `ExpensePersons` is the analytical axis (who the cost is attributed to). Both split by absolute value, no percentages. Two payment methods and two people produce **2 + 2 rows, never 4**. `ClosingDate`/`DueDate` live on the leg, not the expense, because each installment falls in its own invoice; they're derived from the `PaymentMethods` `ClosingDay`/`DueDay` and are null outside `credit_card`.

**Nothing is partially settled.** `Expenses.Status` is derived from the legs and only reaches `'paid'` once *every* leg is paid; `Inflows.Status` goes straight from `'pending'` to `'received'`. Neither table has a `PaidValue`/`ReceivedValue` column and neither has a `'partial'` state. The per-leg `Paid`/`PaidAt` on `ExpensePayments` stay because installments require them — a 6× purchase needs to know which parcels are settled — but that detail is never promoted to a partial status on the parent.

A recurring ("fixed") expense is a **chain of real occurrences**, not template + instances: every `Expenses` row is a real expense. The series root has a null `IdParentExpense` and carries `RecurrenceDay`/`RecurrenceEndDate`; generated occurrences point back at it. This is deliberate — a template row would be a phantom that every report has to filter out.

`Tags` are the temporary taxonomy (a trip, an event) alongside the permanent `Categories`: an expense has one category and N tags. The link table is `ExpenseTags` rather than a generic one so inflows can get their own later without touching `Tags`. `ExpenseTags`→`Tags` is `ON DELETE CASCADE`, so a physical delete would *succeed* and quietly strip the tag off every expense already marked — the `DELETE` route is `Active = false` for that reason, not because the database would refuse.

**A tag has no CRUD of its own — it is born with the expense.** The client sends `Tags` as **text**, and `Tags/sections/POST/resolveByName.ts` turns those strings into rows inside the expense's transaction: an existing name is reused (case-insensitively), an archived one is un-archived, a new one is inserted. So the feature has exactly two routes: `GET /Tags/search` (the suggestion input, ILIKE with the wildcards escaped, capped) and `DELETE`. There is no `POST` because registering a label before using it is two steps for one word, and no `PUT` because renaming a tag would relabel every expense already marked — whoever wants another name types another name on the next expense. That also makes reuse the un-archive path, which is why `Tags` no longer needs the name-check section `Persons` still has.

Both `Persons` and `Tags` carry `unique(IdWorkspace, Name)`, and **that index doesn't know about `Active`**: the archived row keeps its name occupied. Both features look the name up before writing — `PersonName.section.ts` to answer 406 instead of a 23505 as a 500 (the same shape as the free-email check at signup, index still the real guarantee), `resolveByName.ts` to reuse the row instead of inserting a second one. Both comparisons are deliberately *stricter* than the index: case-insensitive (`lower("Name")` in raw, identifier quoted), because "Maria" and "maria" in one split are a typo, not two people. The two differ in what they do with an archived row, and that follows from who names it: a person is a cadastro, so the name stays taken and a 406 says so — if that ever bites, the fix is a restore route; a tag is just typed text, so typing it again brings the row back, which is the only un-archive path either table has.

`Inflows` carries **both** money coming in and transfers between accounts, discriminated by `Kind`: `'inflow'` has a null `IdFromAccount` (the money came from outside) and `'transfer'` requires both accounts, different from each other — two `CHECK` constraints enforce this. Because a transfer is net-zero for net worth, **every "how much came in" total must filter `Kind <> 'transfer'`**, or the same money is counted again each time it moves between accounts. `InflowPersons` splits an inflow across `Persons`; it only applies to `Kind='inflow'`, never to transfers. Inflows have no category and no recurrence by design.

**Current scope.** The schema is complete — all 22 tables above exist in `migrations/`. What is **not** built is the code on top of them: everything through the MVP batch has routes today: `Users`, `Workspaces`/`WorkspaceMembers`, `UsersAuth`/`TrustedDevices`, `Accounts`/`PaymentMethods`, `Categories`, `Persons`, `Tags`, `Inflows`/`InflowPersons` and `Expenses`/`ExpensePayments`/`ExpensePersons`/`ExpenseTags`. `Budgets`/`BudgetPeriods` have routes too, in the reduced shape below (manual monthly registration; the routine that would materialize the month is still to come). What is left without an API is the platform tables: `UserDevices`, `Notifications`, `Plans`, `Subscriptions`.

`Accounts` is the first tenant-scoped feature, so it's the reference for the rest: `IdWorkspace` comes from the session token and every section opens with `WorkspacesAcessControl.assertMember`/`assertRole`, and every `getUnique` filters by `IdWorkspace` *as well as* the row id — the row id is sequential and arrives from the client, so a membership checked on your own tenant would otherwise let you read the neighbour's row. Both DELETEs are `Active = false` — `Inflows`→`Accounts` and `ExpensePayments`→`PaymentMethods` are `ON DELETE RESTRICT`, and the history has to keep pointing at the row that was actually used. **`InitialBalance` freezes once the account has movement** (`Accounts/sections/AccountMovement.section.ts`): with no cached balance there is nothing to recalculate, and moving the opening balance would rewrite last month's statement from underneath.

`Accounts` and `PaymentMethods` are two features, in `routes/Accounts/` and `routes/PaymentMethods/` — **one folder per table, no exceptions**, even when one table is the child of another. They lean on each other in both directions, always through an explicit cross-feature import: creating an account calls `PaymentMethods/sections/POST/createDefaults.ts` inside the account's own transaction (a `pix` and a `debit` row are the model's rule, not a convenience — an account with no payment method can't receive a single expense), archiving an account archives its methods, and `GET /Accounts` embeds them via `joinTables`. `POST /PaymentMethods` only takes `Kind='credit_card'`; `pix` and `debit` are never created by hand. Feature-owned Joi shapes stay with their feature and get imported — the account's response schema imports `paymentMethodResponse` from `PaymentMethods.schema.ts`, so the row is described once. Shapes that belong to no feature (`isoDate`, `color`) live in `Utils/joiSchemas.ts`.

`routes/Categories/` follows that reference and adds the one thing no other feature has: **rows nobody owns.** `GET /Categories` returns the workspace's categories and the global ones together, in one flat list — together because a fresh workspace has only the globals, and splitting them would make the client concatenate two calls to fill one picker. Two rules carry the feature:

- **A global category is read-only** (`sections/CategoryOwnership.section.ts`). `getUnique` finds it — it is visible to every workspace — and `assertEditable` is what refuses the write with a 406 of its own, rather than the row simply being missing. Without it, one `PUT` renames a category for the entire user base and one `DELETE` archives it for everyone; the happy path never touches it, so this is the case every write suite has to carry.
- **Archiving is `Active = false` on one row**, scoped by `IdWorkspace` in the `UPDATE` itself so a stray id can never reach another tenant's row — or a global, which belongs to nobody.

**There is no hierarchy: a category is never the child of another** (migration `20260829010000_drop_categories_parent`). The column existed and was dropped along with everything it dragged behind it — checking that a client-supplied parent was visible to the workspace, refusing cycles (a cycle leaves the branch with no root, so it vanishes from the rendering while staying live and assignable by id), and cascading the archive down the subtree. None of that paid for itself with a dozen categories per workspace, and the flat list has no such failure modes.

### The movement features

`routes/Inflows/` and `routes/Expenses/` + `routes/ExpensePayments/` are where money actually moves, and they share four rules that no earlier feature needed:

- **The period filter is `?From=YYYY-MM-DD&To=YYYY-MM-DD`, inclusive on both ends** (`periodQuery` in `Utils/joiSchemas.ts`), on `CompetenceDate` for inflows and `ExpenseDate` for expenses. A range, not `ReferenceMonth=YYYY-MM`: a month is expressible as a range, but a card invoice period — closing day to closing day — never lines up with the calendar month. Omit `Status` and the canceled rows stay out; ask for `Status=canceled` and they come back.
- **The balance is computed on every read** (`Accounts/sections/AccountBalance.section.ts`), embedded as `Balance` in `GET /Accounts`: opening balance + received inflows in − received transfers out − *paid* expense legs. Pending is a forecast, not a balance. Three grouped queries for the whole list, never one per account. Two traps live in that one file: transfers count on **both** sides here (unlike "how much came in", which excludes `Kind='transfer'`), and the paid-legs query joins `Expenses` to skip canceled ones — canceling a settled expense is the refund, and without that join the money would stay out of the account forever.
- **Money invariants are checked in cents** (`Utils.toCents`): `sum of parts === total` never holds in floating point. Every split closes exactly with the total, and the database enforces none of it.
- **Calendar math goes through moment, and never through a loose `Date`.** `date` columns are typed `CalendarDate` (a string) in `Utils/database.ts`, and `Utils.addMonthsToDate`/`setDayOfMonth` parse `"YYYY-MM-DD"` with moment in strict mode and format it back, so no instant ever escapes — in UTC-3 midnight on the 1st is the 31st of the month before. moment's `add` already clamps to the end of the month (31/01 + 1 month is 28/02); its `date()` does not, so `setDayOfMonth` clamps by hand. A `new Date()` in this path is now a compile error.

`Inflows` carries **both** kinds of money movement, and `InflowKind`/`InflowSplit` are the two sections that hold the rules the `CHECK` constraints only catch as a 500: an inflow has one account and a transfer has two different ones, and a transfer takes no split — nobody's share changed when money moved between your own accounts. Creation always lands `pending`; `POST .../receive` is what puts it into the balance, and it is all-or-nothing (no `partial`, no `ReceivedValue`). Editing a *received* inflow is allowed on purpose — that is what the no-cached-balance decision buys, since there is nothing to correct but the row itself. Both `PUT`s re-check the split against the **new** total even when the split wasn't sent, because when only the total moves it is the stored split that stops closing.

`Expenses` is one POST for three shapes — `single`, `installment`, `fixed` — and three rules carry it:

- **The two axes never mix.** `ExpenseAxes` validates them in separate passes and `GET` returns them as separate lists: two payment methods and two people are **2 + 2 rows, never 4**. Each axis closes with the total on its own. The category is required and checked by id (`ExpenseCategory.section.ts`); the tags arrive as **text** and are resolved by the `Tags` feature inside the same transaction, so an expense is the only thing that ever creates a tag.
- **`Status` is derived, in exactly one place** (`ExpenseStatus.section.ts`), recomputed inside the same transaction as any write to legs and never accepted in a body. It reaches `'paid'` only when *every* leg is paid, so settling 1 of 6 installments leaves the purchase `pending`, and an expense with no legs at all is never `paid` (`every` over an empty array is `true` — that guard is deliberate).
- **Payment dates live on the leg** (`InvoiceDates.section.ts`). On a credit card they are the invoice: buy on or before the closing day and it lands on this month's, after it and it is next month's; the due date rolls a month when `DueDay <= ClosingDay`. One day of difference in the purchase becomes one month of difference in the cash-out. Off the card there is no invoice, so `forPayment` returns nulls — but `forInstallment` still sets a `DueDate` one month apart per parcel, because **installments are not a credit-card privilege**: a store book, a `crediário` or splitting a purchase with a friend land on pix or debit and still have monthly parcels.

Installments are `Kind='installment'` with a **single** leg (any payment method — two legs would need a second axis inside the financial one to say which parcel came from where): 600 in 6× is six rows of 100 with their own invoice dates, `TotalValue` stays the purchase total, and the leftover cents go on the **first** parcel (`Installments.section.ts`) so the legs sum exactly to the total. A fixed expense is a chain of real occurrences — the root is the first one and carries `RecurrenceDay`/`RecurrenceEndDate`, and `Occurrences` (default 12) generates the window ahead so next month is already visible without a scheduler. Series edits (`PUT`/`DELETE .../series`) act on **the occurrence you called them on and every later one**, exactly like "this and following events" in a calendar: the cut is that occurrence's date, never the clock, which keeps "what was I paying in August" answerable and the behaviour verifiable in a test. `POST /ExpensePayments/.../pay` (and `unpay`, which exists because a wrong click otherwise takes money out for good) is the only thing that flips a leg, and it refreshes the derived status in the same transaction.

`docs/ROADMAP- MVP.md` maps the work in stages, ordered by the foreign keys, and records the cross-cutting decisions plus how each stage actually turned out. All four decisions are now settled: the workspace rides inside the token, the balance is computed and never cached, `Expenses.Status` is written only by `ExpenseStatus.section.ts`, and the period filter is `From`/`To`. Read it before starting a new feature — it also carries what is deliberately left open (workspace sharing, and the `Persons` `unique(IdUser)` constraint that assumes one workspace per user).

#### PostgreSQL specifics

V3 was MySQL; V4 is PostgreSQL. Knex handles the DDL translation (`tinyint`→`smallint`, `.unsigned()` ignored, `enu`→`text`+`CHECK`, `binary`→`bytea`, `datetime`→`timestamptz`), but three things bite at the query layer:

- **`Active` is a real `boolean`.** Use `.where("Active", true)` / `.update({ Active: false })`. The MySQL habit of `.where("Active", 1)` throws `operator does not exist: boolean = integer`.
- **`numeric`, `bigint` and `date` are re-typed on read** by `registerPgTypeParsers` (`section/pgTypeParsers.ts`, called from `AppKnex.ts`). Without it node-postgres returns money and bigints as *strings* and `date` as a local-midnight `Date` that shifts the calendar day in UTC-3. Money and counters arrive as `number`; `date` columns (`CompetenceDate`, `DueDate`, `ReferenceMonth`, …) arrive as `"YYYY-MM-DD"` strings — they are calendar dates, not instants, so never wrap them in `new Date()` for display. Note the parsers are registered in the app path only; the Knex CLI (`knexfile.ts`) does not load them, which is fine as long as migrations only do DDL and inserts.
- **Identifiers are case-sensitive.** Knex always double-quotes, so the PascalCase table/column names work through the query builder. Any raw SQL must quote them explicitly (`select "IdUser" from "Users"`), or Postgres will fold to lowercase and fail.

Postgres has no `ON UPDATE CURRENT_TIMESTAMP`, so every model must set `UpdatedAt: KnexConnection.fn.now()` on update, as `Users.model.ts` does.

### Cache subsystem (`routes/Cache/`)

An in-memory, socket-synced cache (`CacheEngine`, singleton `cacheEngine`), not tied to any one feature:

- `cacheEngine.attachConsummer(type, consumer)` registers a bucket ("type") backed by a `CacheConsummer` with `restoreCacheData()` (initial load, e.g. from DB) and optional `formatSet`/`formatGet`/`formatSocket` hooks to reshape data on write/read/broadcast.
- `cacheEngine.setProp`/`getProp`/`reset` are the CRUD entry points, exposed over HTTP by `Cache.route.ts` (`GET /Cache/CacheName=:CacheName`, `POST /Cache`, `POST /Cache/Reset/CacheName=:CacheName`).
- Writes push to socket.io clients that joined the corresponding room. Rooms are `type` or `type.key`; clients join/leave via the `joinCacheRoom`/`leaveCacheRoom` socket events wired in `Utils/socket.ts`.
- Every cache op is separately logged via `Logs.insertCacheLog` into `Logs/cache/<type>.*.log`.

### Socket.io

Runs on its own port (`SOCKETPORT`, separate from the HTTP `PORT`). `Utils/Connections/Socket.ts` has the abstract `SocketEngine` base (default `joinRoom`/`leaveAllRooms` events, `attachDefaultRoute` for subclasses to add more). `Utils/socket.ts`'s `SocketController extends SocketEngine`, adding the cache-room events and outbound helpers (`sendCache`, `sendCacheTo`, `sendTotalCacheTo`).

### Logging

Winston + daily-rotate-file, writing under `Logs/`. `Logs.insertLog(log, type)` logs to `Logs/<type>/<date>.<type>.log` (`type` ∈ `info`/`error`/`userError`/`untracked`/`telemetry`); `insertRotineLog`/`insertCacheLog` log to `Logs/rotines/<name>/` and `Logs/cache/<name>/` respectively. `Logs.handleError` auto-classifies a thrown `APIError` with `status === 406` as `userError`, everything else as `error`.

## Integration tests

There are no unit tests: every suite is an integration test that goes through the real pipeline (`AsyncHandler` → Joi schema → section → Knex → Postgres). Nothing is mocked.

- **One file per feature/table**, next to the feature: `routes/<Feature>/<Feature>.test.ts` (`testMatch: **/*.test.ts`). `routes/Users/Users.test.ts` is the reference. Inside it, **one `describe` per route**, in the same order as `<Feature>.route.ts`, plus a final `describe("Fluxo end to end")` that walks the feature's happy path over HTTP only.
- **Helpers live in `Utils/Tests/`** (barrel at `Utils/Tests/index.ts`): `TestClient`, `TestDatabase`, `TestEnv` and the factories in `section/factories/`.
- **`TestClient`** is the HTTP client. By default supertest boots the app in-process; with `TEST_BASE_URL` set the exact same tests hit a running server (end to end mode) — that's why tests must never call sections/models directly. It sends the token as the `token` cookie — the same and only channel the browser uses — and `client.login(email, password)` authenticates through the real route and picks the token out of the `Set-Cookie` it gets back. The token is the whole session, so the client holds nothing else; to build a session the login can't produce — no workspace selected, or one pointing at someone else's — use `UsersFactory.buildToken(IdUser, IdWorkspace?)`, which is how the suites prove `assertMember` still catches a genuinely signed token whose membership doesn't exist.
- **`TestDatabase`** wraps the test connection: `truncate([...])` (per suite, CASCADE + restart identity), `connection()` for asserting the persisted row, `reset()`/`migrate()`. Every destructive helper goes through `TestEnv.assertTestDatabase()`, which refuses to run unless the database name contains `test` (override with `TEST_DB_UNSAFE=true`). **`truncate(["Users"])` cascades through `Workspaces` into `Categories`, and that empties the whole table — the 13 global rows from the seed migration included, since they live there with a null `IdWorkspace`.** `globalSetup` only re-runs the migrations once per execution, so the first suite to truncate takes the seed away from every suite after it: a suite that needs a global category seeds its own (`Categories.test.ts` does) instead of relying on the migration.
- **Factories** seed direct to the DB (`UsersFactory.create()` returns the row, its workspace, its own `Persons` row, the plaintext password and a valid JWT; `UsersAuthFactory.create(IdUser)` seeds a passkey row). Use them for arranging state; use HTTP for what is under test. `UsersFactory` seeds the workspace, the membership and the owner's person because signup does — each of those is a state the app can't reach without, and seeding one the app never produces would hide the bug instead of finding it.
- **Known gap:** no suite closes the WebAuthn loop, because `register`/`authenticate` need a signature from a real authenticator. `UsersAuth.test.ts` covers everything on either side of the crypto — challenge issuing and binding, who may call what, device state, persistence — and every rejection path. The factory's public key is random, so those credentials list and expire correctly but can never verify.
- **Config**: `Utils/Tests/globalSetup.ts` rolls back and re-runs the migrations once per execution (so the migration seeds are always there); `setupFiles` loads `Utils/Tests/section/TestEnv.ts` before any app module, since `enviromentManager`/`AppKnex` read the env at import time; `setupFilesAfterEnv` destroys the Knex pool at the end of each file. `maxWorkers: 1` because all suites share one database, and `forceExit: true` because importing the app leaves the socket.io server running. The cache `memoryLog` interval is now stopped in `setupSuite.ts` and `unref`ed at the source: it fires once a minute, and a tick landing after Jest tore an environment down surfaced as a winston crash **inside whatever test was running next** — a random red that belonged to no test.
- **`.env.test`** (gitignored, template in `exemple.env.test`) is layered *on top of* `.env` with `override: true` — it only declares what changes in tests (`DB_SCHEMA` pointing at `gastos_mensais_v4_test`, `SOCKETPORT=0` for an ephemeral port, optional `TEST_BASE_URL`).

```
npm test                # app em memória (supertest)

npm run start:test      # terminal 1: servidor apontando para o banco de teste
npm run test:e2e        # terminal 2: mesmas suítes, servidor real
```

`Utils.configEnv()` applies the same `.env` + `.env.test` layering, so the server started with `NODE_ENV=test` and the test process read the identical config — without that the factories would seed one database while the server reads another.
